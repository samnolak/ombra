## Notes

- **Расхождения в документации** (исправить при работе над пунктами): `avalonia/docs/PARITY.md:230` отмечает `get_messages_page` как Done — в коде его нет. `PARITY.md:124` пишет «no RPC for `fork`» — команда есть с 18.4.11 и присутствует в пине 18.8.0. `PARITY.md:125` пишет «needs an RPC for navigateTree» — `get_tree` в пине уже есть.
- **Порядок работ** — все P1 RPC-пункты, кроме `--restore`, работают на текущем пине 18.8.0, обновление omp не нужно:
  1. O1 — дельта-стриминг;
  2. O3 — постраничная история;
  3. O2 — кэш каталога;
  4. O5 — выход при недоступной модели;
  5. O7 — PATH;
  6. O6 — Job Object;
  7. O4 + `--restore` — вместе с подъёмом пака до ≥18.10.3; перед этим прогнать real-omp тесты на изменения конца хода (18.8.7: steer-interrupt больше не шлёт `agent_end`).
- **Upstream-вопрос (omp-core):** в [#3805](https://github.com/can1357/oh-my-pi/issues/3805) мейнтейнер-бот прямо спросил, делать ли `--mode rpc` публичным версионированным API. С 18.5.1 есть машиночитаемая wire-схема `rpc-wire.schema.json` и negotiate v2. Предложение: генерировать из неё C#-DTO и CI-проверку совместимости вместо ручного парсинга `JsonElement`; апстриму предложить политику депрекации.
- **Безопасность удалённого доступа:** у Ompcot LAN/QR открывает HTTP/WS-сервер внутри omp без явной модели доверия (это отмечено и в ответе мейнтейнера в #3805). Если делать удалённый доступ, то только по образцу iris (E2EE ECDH + ChaCha20-Poly1305, демон на 127.0.0.1) или OMPiUI (pairing с rate-limit, лимит тела 413, доверие XFF только явно указанным прокси).
- Решения Ompcot (расширение внутри omp поднимает HTTP-сервер, broker по портам) и iris (отдельный демон + relay) архитектурно нам не подходят: наш stdio-RPC проще и надёжнее. Перенимать стоит только приёмы из таблиц выше.
- Не проверено (не запускалось): реальный выигрыш O1/O2 в цифрах; накопительность `partialResult` в `tool_execution_update` (O8); поведение Bun с путями `\\?\` на Windows (O14).
