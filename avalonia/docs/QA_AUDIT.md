Independent read-only audit; fixes tracked here as they land.

## 1. Ask before closing or quitting while omp is working
`avalonia/src/OmpGui.App/Views/MainWindow.axaml.cs:1142-1151` · priority 1 · confidence 0.9

Severity: major. MainWindow.OnClosing cancels the close and then always awaits vm.DisposeAsync() and calls KillAllTerminals(). It never checks Phase or HasDialog. Closing the window, pressing Cmd+Q, or choosing Quit in the tray menu (App.axaml.cs:131, which calls window.Close()) while a run is going, or while omp waits for an approval, stops omp (stdin EOF, then the process tree is killed) and kills every shell tab, such as a running dev server. The user gets no warning. Restart to update already refuses during a run (MainViewModel.Updates.cs:226 'Stop the current run first'), so this path is inconsistent with it. On macOS, closing the window also quits the app because of the default OnLastWindowClose shutdown mode. Fix: in OnClosing, when !_closeConfirmed and (vm.Phase is Running or Aborting, or vm.HasDialog, or any live terminal tab), set e.Cancel = true and show an in-window confirmation: 'omp is still working. Quit and stop the run? / Keep working'. Only on confirm set _closeConfirmed and continue with the current dispose path. Add a headless test that closing while Running shows the prompt and does not dispose the session.

Status: fixed — Views/MainWindow.Closing.cs (OnClosing asks while Running/Aborting, HasDialog or a live terminal tab; restores a minimized window first; Updates → Restart now, already refused during a run, closes without asking since the update script is waiting), ViewModels/MainViewModel.Quit.cs (the question on the session card: Quit / Keep working, Esc = keep, focus on Keep working, the covered card comes back), tray Quit and ⌘Q/⌘W reach it through Window.Close; verified by WindowSafetyTests.Closing_while_omp_works_asks_first_and_only_quit_stops_it, Keep_working_puts_back_the_card_the_question_covered, Closing_an_idle_window_asks_nothing, UiTests.Closing_while_minimized_brings_the_window_back_to_ask_then_stops_omp, TerminalUiTests (live shell asks), screenshot quit-confirmation.png.

## 2. Stop Esc in unrelated text boxes from aborting the run
`avalonia/src/OmpGui.App/Views/MainWindow.axaml.cs:1082-1086` · priority 1 · confidence 0.85

Severity: major. MainWindow.OnKeyDown aborts the run on any Esc that bubbles up while Phase is Running, unless the image viewer, shortcut sheet, a focused dialog or Settings handled it first. Several text boxes never handle Esc: the sidebar's SessionFilterBox (MainWindow.axaml:133), the preview's AddressBox (Controls/PreviewPanel.axaml:54), and the Files pane filter once it is empty (FilesPane.axaml.cs:142 handles Esc only when HasFilter). The terminal tab may also let Esc through ([INFERENCE]: the third-party Iciclecreek TerminalControl wasn't decompiled). To reproduce: start a long run, click the sidebar search, type and clear it, press Esc. The agent's run is aborted when the user only meant to leave the search box. Fix: before the abort branch, if FocusManager.GetFocusedElement() is a TextBox other than Composer (or is inside TerminalHost or PreviewPanel), clear or blur it (focus Composer) and set e.Handled, without aborting. Keep 'Esc stops the run' only when focus is in the composer, the transcript, or nothing. Update the Esc row in USER_GUIDE.md's shortcuts to match.

Status: fixed — Views/MainWindow.Escape.cs (EscapeStaysLocal: a non-composer text box hands focus back to the composer, the terminal and the preview keep the key, the session card's Esc is its ×) called before the abort branch in MainWindow.OnKeyDown; USER_GUIDE Stop and Esc rows; verified by WindowSafetyTests.Esc_in_the_sidebar_search_leaves_it_and_does_not_stop_the_run (and Esc from the composer still stops) and Esc_in_the_terminal_stays_with_the_shell.

## 3. Log client exceptions to a file and include them in the diagnostics zip
`avalonia/src/OmpGui.App/App.axaml.cs:36-41` · priority 1 · confidence 0.9

Severity: major. The only crash handling is Dispatcher.UIThread.UnhandledException, which writes to Console.Error and sets Handled=true. A packaged macOS app has no visible stderr. Nothing hooks AppDomain.CurrentDomain.UnhandledException or TaskScheduler.UnobservedTaskException (grep finds neither in src). The Settings → Diagnostics zip (DiagnosticsBundle.Entries: about, settings, runtime, session, install.log, startup.log) has no record of the app's own errors. So every exception escaping an AsyncRelayCommand or an async void handler (OnDrop, OnClosing, PreviewPanel.OnWebNavigationCompleted, CodeView.Copy) vanishes silently, and a crash on a background thread ends the process with no trace. Beta testers can't report what went wrong. Fix: add a small rotating client log (for example ~/Library/Logs/OMP GUI/client.log, 1 MB × 2) written from all three handlers with a timestamp and the full exception. Add 'client.log' to DiagnosticsBundle.Entries (redacted like the others). Optionally set a one-line, non-modal notice ('Something went wrong — Settings → Diagnostics') the first time a UI exception is swallowed.

Status: fixed — Services/ClientLog.cs (client.log + client.1.log, 1 MB each; macOS ~/Library/Logs/OMP GUI, else LocalAppData/OmpGui/logs, OMPGUI_LOG_DIR), AppDomain + TaskScheduler hooks in Program.Main, the Dispatcher handler in App.axaml.cs logs through MainViewModel.ReportClientError and says it once under the message box; DiagnosticsBundle adds client.log (redacted like every entry); USER_GUIDE Diagnostics and "Where things are kept"; verified by WindowSafetyTests.Client_errors_are_kept_in_two_rotating_files and A_ui_error_is_logged_said_once_and_in_the_diagnostics_redacted.

## 5. Let users revert omp's changes per file or hunk from the diff view

Severity: major (gap next to Codex and Claude Code desktop). The Files pane can list changed files (FilesViewModel 'changes' and session-changed modes) and show a diff, but there is no action to revert a file or hunk, stage, or comment on a line. Grep for revert/discard/restore in FilesViewModel finds nothing. Codex's review pane stages or reverts single hunks or whole files and takes inline comments (https://codexhandbook.com/en/guide/desktop-app/diffs-comments-and-review/). Claude Code desktop has a rebuilt diff viewer with review comments (https://www.macrumors.com/2026/04/15/anthropic-rebuilds-claude-code-desktop-app/). Add 'Comment on line', which adds a chip to the composer the way page comments do. Refresh git marks afterwards through the existing RefreshAsync.

Status: fixed — the viewer had no diff mode, so one was added: ViewModels/FileViewerViewModel.Review.cs (a file git sees changed gets File · Changes +N −M, opened from Changed/This session it starts on Changes; rows per hunk with Revert, lines coloured, "+" per line opens a comment box; Revert file… / Delete file… ask in a notice first; FilesViewModel.SyncViewerGit keeps the mark and reloads the diff on every refresh, RevertHunkAsync/RevertFileAsync then RefreshAsync for the marks), Services/GitDiff.cs (git diff HEAD with --no-ext-diff --no-textconv, --no-index for untracked; a hunk + file header as its own patch, `git apply -R` through MainViewModel.RunTool/ToolCommand, then `--cached` so a staged hunk leaves the index too; `git restore --source=HEAD --staged --worktree`, an untracked file is deleted), Controls/DiffLineText.cs, Views/Panes/FilesPane.axaml(.cs) (Enter adds / Esc closes the comment box), ViewModels/MainViewModel.CodeComments.cs (chips like page comments, sent after the message with file, line and the line's text; RowViewModels shows them as "N comments on the code"), Styles.Files.axaml, USER_GUIDE.md (Files pane), DESIGN_SYSTEM.md (Changes row); interaction follows Codex (hunk Revert, hover "+" per line, per-file revert) and Claude Code desktop (comment box, Enter adds). ## 10. Don't lose the composer content when a send fails with InvalidOperationException
`avalonia/src/OmpGui.App/ViewModels/MainViewModel.cs:236-257` · priority 3 · confidence 0.6

Severity: minor ([INFERENCE] the timing window is narrow). SubmitAsync takes the composer content (take() clears the text and attachments), sets Phase to Running optimistically, then awaits _session.PromptAsync or QueueAsync. Both start with RequireConnection(), which throws InvalidOperationException('omp is not running') when _omp is null. That happens between `_omp = null` and the new start in SessionController.RestartAsync (approval-mode change, Recover, Save and restart), before the UI has applied the Stopping/Starting phase. SubmitAsync only catches OperationCanceledException. The exception goes to the dispatcher handler (stderr only), the typed message and images are lost, and SettleOptimisticPhase never runs. Fix: in SessionController.PromptAsync and QueueAsync, add an error notice and return instead of throwing when there is no connection. Or catch InvalidOperationException in SubmitAsync, put the text and attachments back in the composer, and call SettleOptimisticPhase().

Status: fixed — ClientCore/OmpNotRunningException.cs thrown by SessionController.RequireConnection; SubmitAsync and SteerAsync catch it, put the text and images back in the box (ViewModels/MainViewModel.Unsent.cs, with a message under it) and settle the optimistic phase; verified by WindowSafetyTests.A_message_omp_never_got_goes_back_into_the_box.

## 12. Add a stall timeout to runtime pack downloads
`avalonia/src/OmpGui.App/App.axaml.cs:43-43` · priority 3 · confidence 0.75

Severity: minor. RuntimeInstaller gets `new HttpClient { Timeout = Timeout.InfiniteTimeSpan }`, and SelfTest does the same at SelfTest.cs:65. If a connection stalls (open socket, no bytes), the omp runtime install shows its last progress forever until the user notices and presses Cancel. The `--self-test --install-runtime` CLI path, used in packaging, has no Cancel at all. Fix: keep the infinite total timeout for large packs but add an idle timeout per read. Wrap each ReadAsync in a CancellationTokenSource.CreateLinkedTokenSource(ct) with CancelAfter(60 s) that is reset after every chunk. On expiry report 'download stalled — try again'.

Status: fixed — RuntimeInstaller.DownloadBunAsync: one linked CancellationTokenSource with CancelAfter(StallTimeout = 60 s) re-armed after every chunk, also covering the wait for the headers; a stall fails with TimeoutException "The download stalled (no data for 60 s). Check the connection and try again." — the app shows it as "Installation failed: …", and --self-test --install-runtime uses the same installer; verified by RuntimeInstallerTests.A_download_that_stops_sending_fails_as_stalled_and_leaves_nothing and A_slow_download_that_keeps_sending_is_not_cut_off.
