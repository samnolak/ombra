- **Не конкурент чату или мессенджеру.** Сложные обсуждения идут в отдельных продуктах. У нас только быстрый обмен и комментарии в духе Figma со статусами (сценарий [P5](#p5-как-работает-обмен--обязательный-сценарий-уточнение-владельца-2026-10-18)).

## P. Общая платформа: участники, команды, синхронизация

Основа для K2, K4, B1 и B2. Без неё каждый продукт сделает свою модель, и связать их потом будет дороже.

**Заменено решением владельца (2026-10-18).** Прежнее уточнение о Git-командах ([ARCHITECTURE_SOLUTIONS §10](ARCHITECTURE_SOLUTIONS.md#10-принятое-уточнение-git-команда-общение-и-обмен-инструментами)) в этом релизе не действует.
- Команды — только собственные (P1, P2): участник с ID и именем, создатель — владелец, владелец добавляет и удаляет участников, владение передаётся.
- Git-провайдер как источник состава и прав команды — не делаем в этом релизе.
- Из §10 остаются обмен по P5 и привязка проекта к репозиторию по remote URL.
- Общение, mentions, лента активности, MCP-рецепты, reproduction recipes, библиотека ресурсов и запрос merge — не делаем ([принцип](#принцип-владелец-2026-10-18)).

### P1. Участник: ID и имя

**Зачем.** Чтобы собираться в команды и адресовать правки и ссылки конкретному человеку.

**Требования:**
- При первом входе в любом из двух продуктов создаётся **участник** — собственный, не учётная запись Git-провайдера (вход через Git-провайдер не делаем в этом релизе, решение владельца 2026-10-18):
  - `memberId` — стабильный, случайный, ULID или UUIDv7, не выводится из почты или железа;
  - `displayName` — обязательное, задаётся пользователем;
  - аватар — опционально, инициалы по умолчанию.
- Один участник — несколько **устройств** и **клиентов** (GUI, браузер): у каждого свой `deviceId` и ключ, привязка
  к участнику через код или QR. Отвязка устройства из настроек.
- ID можно скопировать: «Мой ID» в настройках обоих продуктов, формат для передачи — короткий `ab12-cd34-ef56`
  плюс полный в QR.
- Имя видно в командах, у отправителя ссылки или правки, в прогрессе.
- Без участника оба продукта работают как сейчас, полностью локально. Вход опционален и выключается.

**Данные:**
```
Member  { memberId, displayName, avatar?, createdAt }
Device  { deviceId, memberId, product: gui|browser, publicKey, name, lastSeenAt }
```

**Безопасность.** Ключи устройств лежат в системном хранилище: macOS Keychain, Windows DPAPI/Credential Manager,
libsecret. В браузере — `OSKeyStore` Firefox (модуль есть в `engine`, используется formautofill).

### P2. Команды (рабочие пространства)

**Требования:**
- Команды — только собственные: состав и права задаёт владелец в нашем продукте, Git-провайдер их не определяет (решение владельца, 2026-10-18; Git-команды — не в этом релизе).
- Любой участник создаёт команду и становится её **владельцем**.
- Владелец:
  - добавляет участников по ID или приглашением (ссылка или код с TTL) и удаляет их;
  - назначает **причастность**: к каким проектам команды участник имеет доступ и с какой ролью — `viewer` (видит
    прогресс), `contributor` (отправляет правки и задачи);
  - **передаёт владение** другому участнику. Передача подтверждается обеими сторонами, старый владелец становится
    обычным участником.
- Участник выходит из команды сам. Владелец выйти не может, пока не передал владение.
- Удаление команды — только владельцем, с подтверждением вводом имени команды.
- **Проект команды** — это привязка локальной папки или репозитория участника к проекту команды. Привязка идёт по
  remote URL git, а при его отсутствии — вручную. Локальный путь на сервер не уходит.

**Данные:**
```
Team        { teamId, name, ownerId, createdAt }
Membership  { teamId, memberId, role: owner|member, addedBy, addedAt }
TeamProject { projectId, teamId, name, repoFingerprint? }      // repoFingerprint = hash(normalized remote URL)
Access      { projectId, memberId, level: viewer|contributor }
Invite      { code, teamId, createdBy, expiresAt, maxUses }
AuditEvent  { teamId, actorId, kind, payload, at }             // добавление, удаление, передача владения, смена доступа
```

**UX:**
- В GUI — раздел «Команды» в сайдбаре: команды, их проекты, участники с точками статуса.
- В браузере — то же в боковой панели. Управление — в настройках обоих продуктов.

### P3. Прогресс по проектам в реальном времени

**Требования:**
- GUI публикует события прогресса сессий, которые относятся к проекту команды. Публикация **opt-in на уровне проекта**:
  - кто работает: участник и устройство;
  - фаза: working / needs input / idle / error;
  - текущий шаг плана (todo);
  - сколько шагов сделано;
  - изменённые файлы — только имена;
  - время последней активности.
- **Не публикуются** без отдельного явного включения: текст промптов и ответов, содержимое файлов, diff.
- Участник команды видит **прогресс, отфильтрованный по проекту** (фильтр по проекту, участнику и статусу).
  Прогресс — не операция MLS и не хранится на сервере: снимок шифруется ключом из MLS-Exporter группы проекта,
  подписывается устройством и идёт через существующий ephemeral-канал сервера; живёт только в памяти. Догона с курсора
  нет: когда пир появляется онлайн, издатель переотправляет текущий снимок. Публикация — opt-in
  (design-sync-decision §8).
- Presence: онлайн / неактивен / офлайн.

**Сообщение прогресса** (реализовано, `ombra-core/src/progress.rs`, операции `progress.seal` / `progress.open`):
```
подписано Ed25519 ключом устройства: "ombra/v1/progress" ‖ 0 ‖ groupId ‖ epoch ‖ projectId ‖ memberId ‖ deviceId ‖
  status (working | waiting | idle) ‖ updated ‖ projectName ‖ task (пусто, если название задачи не включено)
на проводе: 0x01 ‖ epoch ‖ nonce ‖ AES-256-GCM(MLS-Exporter("ombra/v1/progress", groupId, 32), …)
```
Получатель принимает сообщение только для своего текущего epoch группы проекта, от устройства-ретранслятора, которое
является листом группы и активным устройством названного участника в проверенном roster, с верной подписью и временем
не из будущего. Сервер видит только шифротекст и рассылает его онлайн-листьям (`POST /v1/groups/{gid}/ops`,
`ephemeral = true`), ничего не сохраняя.

**В GUI** (`TeamProgress` в ClientCore, `TeamProgressViewModel` в приложении): проект команды — группа MLS типа
`project` (`TeamClient.CreateProjectAsync`, доступ всем участникам; админ добирает новых участников). В Settings ›
Account у каждого локального проекта — выбор проекта команды и два переключателя, оба выключены по умолчанию:
«Делиться прогрессом» и «Добавлять название текущей задачи». Издатель раз в секунду берёт состояние открытых сессий
проекта (ждёт ответа → waiting, работает → working, иначе idle; задача — текущий пункт плана) и шлёт только изменения.
На странице «Команда» — «Прогресс по проектам» с фильтром по проекту; записи офлайн-устройств убираются.
Фаза error, счётчик шагов и имена изменённых файлов пока не публикуются.

### P4. Общая база и синхронизация между продуктами

**Требования:**
- Сущности, общие для GUI и браузера: участник, команды, проекты команды, **группы** (B1), **отправленные ссылки и
  правки** (B2, K4). Галерея B3 не синхронизируется (принцип).
- Локально у каждого устройства своя реплика в `state.db` ombra-core (SQLite, построчное AES-GCM, отдельный ключ на
  команду для локального стирания D-5). Сервер — только релей шифротекста и очередь доставки (SERVER_DESIGN §3.0, D-7):
  он не хранит историю и не является источником правды; правду строит каждая реплика из подписанных операций.
- Офлайн-первый подход: своя операция применяется к реплике сразу при постановке в outbox и уходит, когда появляется
  связь; повтор — те же байты, после 409 epoch-conflict — повторное запечатывание с тем же opId/seq/rev. Sync идёт до
  `More=false`, курсор хранится в state.db, ack — только после коммита (окончательный отказ — ack + журнал безопасности,
  временный сбой — без ack). Окно дедупликации — 37 дней (очередь сервера 30 дней + 7).
- Конфликты: правит только автор, по `rev`; одинаковый `rev` с двух устройств автора — автоматический победитель по
  `(seq, deviceId)`, на проигравшем устройстве — плашка «правка заменена правкой с другого устройства» с копией текста.
  Статусы: у ресурса окончателен первый финальный (`accepted`/`declined`), у метки побеждает последний
  (`done`/`dismissed`), `seen` ставится один раз. Отдельной операции разрешения конфликтов нет.
- Между GUI и браузером на одной машине — тот же сервер. Прямой локальный канал (native messaging или localhost)
  только для управления браузером агентом (K1), не для данных. **Исключение (решение ведущего, 2026-10-18, ради срока):**
  Nightly не заводит своё устройство команды и делится через Ombra на том же Mac по аутентифицированному локальному
  Mach-каналу (B1/B2, [SERVER_DESIGN §7](SERVER_DESIGN.md#nightly)); без запущенной Ombra обмен в Nightly выключен с причиной.

**Оценка P1–P4.** MVP: участник, команды, приглашения, передача владения, прогресс, доставка ссылок и правок —
**2–4 недели** после решения D1.

### P5. Как работает обмен — обязательный сценарий (уточнение владельца, 2026-10-18)

Один и тот же сценарий для всего, чем делятся участники: K4 (метки и правки), B2 (ссылки и вкладки), B1 (командные группы), ресурсы (файлы и skills). Обмен MCP-рецептами и reproduction recipes из [ARCHITECTURE_SOLUTIONS §10.3](ARCHITECTURE_SOLUTIONS.md#103-обмен-mcp-skills-кодом-и-ресурсами) не делаем (принцип). Протокол и права — [SERVER_DESIGN §3.0](SERVER_DESIGN.md#30-что-передаётся-элементы-а-не-переписка-уточнение-владельца-2026-10-17).

**1. Отправка.** Отправитель выбирает объект и нажимает «Поделиться». Объектом может быть:
- файл, skill, ссылка или вкладка, снимок, правка или патч, коллекция (в том числе группа вкладок);
- метки и комментарии на документе, файле или вкладке.

Затем он выбирает получателей — «Все» (пространство команды или проекта) или конкретных участников — и отправляет.

**2. Уведомление.** Получатель видит toast: кто и чем поделился. Формулировки:
- «Анна поделилась файлом / skill / ссылкой / снимком / правкой / коллекцией "…"»;
- «Анна оставила вам комментарии в <документ / файл / вкладка>». Несколько меток одного автора на одном объекте собираются в один toast.

Пропущенные toast-ы не теряются: всё полученное лежит во **«Входящих»** с фильтрами по типу, автору, проекту и статусу. Входящие — одни на GUI и браузер.

**3. Ресурсы — файлы, skills, ссылки, снимки, правки и патчи, коллекции.** Получатель явно нажимает **«Принять»** или **«Отклонить»**.
- До «Принять» ничего не появляется в его workspace и ничего не становится активным, особенно skill. Видно только карточку во Входящих с предпросмотром: что внутри, автор, версия, для skill — scripts, команды и зависимости.
- Отдельного карантина нет: решение — сама кнопка «Принять».
- После «Принять» объект появляется в workspace: файл — в выбранной папке проекта, skill — в ресурсах проекта, ссылка — открывается во вкладке, патч — в Review с base commit, коллекция — в браузере как группа вкладок. Запуск scripts из принятого skill идёт по обычным разрешениям агента.
- «Отклонить» убирает карточку из активных Входящих; объект не скачивается и не сохраняется.

**4. Метки и комментарии.** Toast или запись во Входящих ведёт **на место**: страница со скроллом к элементу, файл на нужной строке, документ на нужном фрагменте.
- Открытие помечает метки прочитанными.
- Дальше получатель может поставить статус «Сделано» или «Отклонено» с необязательной короткой заметкой (до 280 символов).
- Тредов, ответов и переписки нет; новая мысль — это новая метка.

**Статусы.** У каждого получателя свой статус. Автор видит сводку и статус каждого получателя с заметкой.

| Действие получателя | Статус | К чему применимо |
|---|---|---|
| Открыл метку на месте | `seen` | метки и комментарии |
| «Сделано» | `done` | метки и комментарии |
| «Отклонено» у метки | `dismissed` | метки и комментарии |
| «Принять» | `accepted` | ресурсы |
| «Отклонить» у ресурса | `declined` | ресурсы |

При адресной отправке получатель не видит других получателей и их статусы. При отправке «Все» статус ставит каждый, кто откликнулся.

**Критерии приёмки P5:**
- Отправка файла, skill, ссылки, снимка, патча, коллекции и метки конкретному участнику и всем: у получателя toast с верной формулировкой и запись во Входящих.
- Skill и файл не видны в workspace получателя и не активны до «Принять»; после «Принять» — видны и доступны; после «Отклонить» — ничего не скачано.
- Метка открывается на якоре, получает `seen`; `done`/`dismissed` с заметкой видны автору у этого получателя.
- Toast, пропущенный офлайн, находится во Входящих после выхода в сеть.
- Ответить меткой в тред нельзя: такого действия нет в UI.

### P6. Обновления git от команды (боль владельца, 2026-10-18)

Закрывает боль из [принципа](#принцип-владелец-2026-10-18): коллега запушил — я узнаю и обновляюсь так, чтобы наши изменения не пересеклись и не затёрлись. Без своего git-сервиса: обычный `git fetch` с учётными данными пользователя.
- Колокольчик в заголовке окна: по каждому репозиторию открытых чатов — новые коммиты upstream текущей ветки (сколько, авторы, файлы) и новое в ветке по умолчанию, пока я на feature-ветке; в том же списке — ожидающие элементы командных «Входящих» (P5).
- Фоновый `git fetch --quiet` без merge и без запросов пароля: каждые ~5 минут, при фокусе окна и после хода агента — только для доверенных папок (Workspace trust), недоверенные — по кнопке «Проверить сейчас». Локальная конфигурация репозитория не может ничего запустить (sshCommand, credential helper, upload-pack, filter/merge driver заменяются пользовательскими или отключаются). Выключается в настройках; при строгой сетевой приватности не выполняется.
- Обновление считает риск: чисто → `git pull --ff-only`; незакоммиченные изменения в других файлах → тот же fast-forward: git оставляет их на месте и до записи проверяет каждый файл, при угрозе изменению ничего не трогает (без stash, reset и clean); пересечение файлов или разошедшаяся история → не обновляем, показываем файлы, предлагаем «Попросить агента обновить» или «Показать входящие изменения». Во время хода агента в этом репозитории обновление ждёт конца хода; пока идёт обновление, новые ходы там не начинаются. Перед отправкой сообщения в отстающей ветке — ненавязчивая подсказка.

**Статус P6:** сделано (клиент). Тесты на реальных репозиториях (bare remote + два клона), en/ru UI, нативный feature-smoke `git-bell`.

**Статус P (2026-10-18, итог релиза):** P1 сделано — только собственные команды (ID и имя, владелец добавляет/удаляет, передаёт владение; Git-провайдер вне релиза): идентичность устройства, сопряжение (SAS/QR), отзыв с каскадом, передача ключа админа, вход в следующие команды, хранилища ключей Windows/Linux реализованы (агент TeamsCore-2; нативная приёмка DPAPI/libsecret — release gate). ## K. Кодинг-агент

### K1. Nightly внутри Ombra: аннотации и управление · P1

**Цель.** Один Nightly runtime для самостоятельного браузера и всего встроенного браузера Ombra, включая
текущий preview и responsive web-режим K3. Пользователь работает прямо в Ombra без ручного подключения.
Выбран отдельный Gecko host с GPU surface в Avalonia; это замена движка preview, не дополнительный backend.

**Размещение (принцип владельца, 2026-10-18).** Nightly развивается как отдельный продукт и встраивается. В агенте браузер открыт в правой панели, его используют инструменты агента, аннотации сохраняются. Для самостоятельной работы браузер открывается из левого rail. Вынос вкладки в отдельное окно не делаем.

**Что уже есть** (GUI, встроенный preview):
- `NativeWebView` в `PreviewPanel`: WKWebView/macOS, WebView2/Windows, WebKitGTK/Linux; Tern host в
  `Browser/TernHost.cs` и `TernBlock.cs`, его нынешний page adapter — macOS-only; есть старый cmux bridge.
- на macOS — нативный ввод (`Platform/Mac/NativeInput`), диалоги страниц, загрузки, HTTP auth;
- аннотации страниц: точка или область, селектор, источник для React/Vue/Svelte, привязка к маршрутам SPA
  (`PreviewAnnotations.cs`);
- вкладки и размеры устройств.

**Что сделать:**
1. **Локальный bridge Ombra ↔ Nightly.** Наш fork omp вызывает host-browser API GUI, GUI маршрутизирует
   операции в привилегированный компонент Nightly. Model-facing browser API сохраняется.
   - общий versioned runtime pack, обнаружение совместимой установки, version handshake и автоматический bootstrap;
   - Unix socket / Windows named pipe с правами пользователя, секрет не доступен страницам;
   - созданные в Ombra вкладки связаны с workspace/session без ручной передачи; личные вкладки не выдаются агенту;
   - browser-parent/actor API и штатный доверенный ввод, не синтетический page-JS click;
   - disconnect завершает операции ошибкой; reconnect не повторяет действия с побочными эффектами;
   - BiDi допустим для проверки возможностей, но общий debugging port не является моделью безопасности продукта.
2. **Аннотации в Nightly:**
   - тот же режим, что в preview: точка или область, комментарий, селектор, URL, маршрут, снимок области;
   - хранение — в боковой панели Nightly «Аннотации» по URL и проекту;
   - отправка — «агенту в чат X» (через GUI) или «участнику / в команду» (K4).
3. **Индикация управления.** Когда агент управляет вкладкой: рамка вкладки, значок агента и кнопка «Остановить агента
   в этой вкладке». Ввод пользователя во время действия агента ставит агента на паузу.
4. **Согласие по сайту** (как в Claude 2.1.288 и 2.1.296). Чтение и скриншоты — без вопроса. Click, type, eval и
   навигация на залогиненных сайтах вне localhost — с карточкой «once / session / always».
5. **Браузерная панель.** Адрес, навигация, вкладки, интерактивное изображение и ввод Nightly внутри Ombra.
   Вынос в отдельное окно — не делаем (принцип); самостоятельная работа — из левого rail; один владелец
   профиля и ввода. Нынешний preview переезжает на тот же Nightly runtime; второй browser engine не сохраняется.
   Проверить compositor capture, скрытый host, IME/focus, DPI/resize, clipboard, drag/drop, popup/dialogs,
   files/downloads, audio/video и accessibility. Протокол управления сам по себе не реализует эту панель.
6. **Cutover существующего браузера.** Перенести `PreviewPanel`/`PreviewTab`, agent pages, popups, web-device preview,
   hooks/dialog broker, auth/downloads/permissions, annotations, isolated scripts, capture/PDF и viewport/UA.
   Удалить заменённые WebKit/WebView2/WebKitGTK adapters и WebView dependency после миграции всех потребителей;
   в fork omp убрать скрытый Chromium fallback. Историю/вкладки/аннотации сохранять; поддерживаемый импорт
   web storage/cookies определить явно, не обещать автоматический перенос авторизации сайтов между движками.
7. **Общие оптимизации.** Одна сборка Gecko и shared browser services для обеих оболочек; tab lifecycle/cache/
   scheduling не должны существовать только в UI Nightly. B4 измеряет standalone и embedded, включая цену
   surface transport. Улучшение интерфейса Nightly само по себе не ускоряет Avalonia.

**Критерии приёмки:**
- Из Ombra без ручного pairing открывается страница Nightly прямо в панели; агент читает её, кликает, вводит
  и снимает через прежний model-facing `browser` API. Та же вкладка доступна из правой панели и из левого rail.
- Аннотация из Nightly приходит в чат GUI с селектором и URL так же, как из preview.
- Пользовательский ввод во время действия агента ставит его на паузу; кнопка «Остановить» работает.
- Переход на чужой домен с вводом спрашивает согласие.
- Автоматическое подключение не даёт доступ к личным вкладкам/другому workspace; Stop/disconnect отзывает
  управление; reconnect не повторяет submit. Без runtime доступны чат/редактор и установка browser pack, не старый движок.
- Проверены интерактивность без внешнего окна, IME/DPI/dialogs, задержка и расход ресурсов на трёх ОС;
  работа только в отдельном окне не считается выполнением встроенного сценария.
- Обычный preview, web-режим K3 и browser tools используют тот же проверенный Nightly runtime build;
  функции прежнего браузера сохранены, скрытого fallback в WebKit/Chromium нет. Приложения независимы;
  для встроенного браузера не требуется ручной запуск самостоятельного Nightly.
- Полный сценарий «только Ombra»: несколько вкладок с созданием/закрытием/переключением, адресная строка,
  назад/вперёд/reload, сохранение и восстановление вкладок после перезапуска. Сайты, загрузки, popups и агент
  работают без открытого самостоятельного Nightly; runtime запускается автоматически в фоне.
- На чистой установке runtime доступен из поставки Ombra либо устанавливается через неё при первом
  использовании браузера. Ручная установка/настройка самостоятельного Nightly не обязательна.
- Самостоятельный Nightly работает независимо; вкладки, открытые из левого rail, — те же вкладки общего runtime,
  а не копия страницы.

**Риски.** Встраиваемая поверхность Gecko, скрытый рендер и платформенный ввод ещё не доказаны. Не считать
перенос OS-окна кроссплатформенным решением. Для цикла проверки Firefox-форка нужно тестовое окружение без
полной пересборки, где это возможно (например artifact build для совместимых изменений).

**Оценка:** прежние 1–2 недели не учитывали интерактивную поверхность; переоценить после proof. **Зависит от:** D4 renderer/input proof.

**Статус K1 (2026-10-18):** сделано на macOS. Панель Nightly по умолчанию с согласием пользователя, закреплённый runtime-пакет (`runtime/nightly/nightly-runtime.json`, sha256), запасной режим с причиной, страница Browser в rail, диалоги/HTTP-вход/разрешения/загрузки/выбор файла карточками, инструменты агента на Nightly, popup/window.open/IME/курсор. ### K3. Эмуляция Android и iOS в клиенте · P2

**Цель.** Верстать мобильные приложения без запуска Xcode или Android Studio. Быстро, без «миллиона часов».

**Отложено владельцем (2026-10-18).** Нативные Android и iOS в этом релизе не начинаем. Web-устройство переезжает вместе с preview в K1. Описание ниже сохранено как задел.

**Факты и ограничения:**
- **iOS Simulator есть только на macOS и только в составе инструментов Xcode.** Легального лёгкого способа запускать
  iOS-приложения без них нет. Сделать можно другое: не открывать Xcode и Simulator.app, а держать simulator
  загруженным в фоне и показывать его экран в нашей панели.
- **Android Emulator** работает на всех ОС. Он умеет `-no-window` (headless) и snapshot-загрузку за секунды.
- **Для web, React Native web и Expo web** уже есть preview с размерами устройств. В следующем релизе
  этот режим тоже использует общий Nightly runtime (K1), а не прежний отдельный WebView; это не Android/iOS эмулятор.

**Режимы панели «Устройство»:**
1. **Web-устройство** (есть, доработать):
   - рамка устройства;
   - safe area (вырез и home indicator);
   - имитация touch: курсор-кружок, жесты прокрутки;
   - DPR;
   - тёмная тема устройства (`prefers-color-scheme`);
   - поворот.
2. **Android (нативный):**
   - SDK находится сам (`ANDROID_HOME`, стандартные пути). Если его нет — «Установить минимальный набор»:
     cmdline-tools, один system image (arm64 на Apple silicon), примерно 1–2 ГБ;
   - AVD «OMP Phone» создаётся сам, запуск `emulator -avd … -no-window -no-audio -gpu host` со snapshot;
   - экран — видеопоток в нашу панель (протокол scrcpy через adb: H.264 → декодер платформы), ввод мышью и клавиатурой
     через тот же канал;
   - быстрые действия: установить APK из проекта, перезапустить приложение, logcat внизу, поворот, тёмная тема,
     скриншот в галерею (B3);
   - hot reload — средствами фреймворка (Flutter, RN), мы только держим эмулятор тёплым.
3. **iOS (только macOS):**
   - проверка инструментов: `xcode-select -p`, `xcrun simctl list runtimes`. Если чего-то нет — понятная карточка, что
     и как поставить;
   - `xcrun simctl boot <udid>` без Simulator.app. Экран — через `simctl io <udid> recordVideo` или поток кадров
     (`idb`); ввод — через `idb ui tap/swipe/text`, потому что в `simctl` нет ввода;
   - быстрые действия: установить `.app` из build-каталога, `simctl openurl`, переключение appearance
     (`simctl ui appearance`), status bar (`simctl status_bar override`), скриншот в галерею;
   - устройство остаётся загруженным между запусками GUI (опция), поэтому холодный старт происходит один раз.

**Скорость (цели):**
- повторное открытие Android-эмулятора со snapshot — ≤5 с;
- iOS при загруженном simulator — ≤1 с до первого кадра;
- задержка ввода — ≤80 мс;
- CPU в простое, когда панель скрыта, — около 0: поток останавливается, устройство остаётся загруженным.

**Агент.** Инструмент через `set_host_tools` (штатный RPC omp): `device_screenshot`, `device_tap`, `device_type`,
`device_install`, `device_logs`. Агент видит результат своей вёрстки.

**Критерии приёмки:**
- Android: от кнопки до интерактивного экрана в панели ≤30 с при холодном старте и ≤5 с со snapshot; клик и ввод
  работают; APK из проекта ставится одной кнопкой.

**Оценка:** web-режим 2–3 дня; Android ~1 неделя; iOS 1–2 недели.

### K4. Запросы и правки через режим аннотаций: в коде и на страницах · P2

**Цель.** Тем же жестом, что аннотация, отправить задачу или правку агенту, участнику или команде.

**Уточнение владельца (2026-10-17).** Это не лента комментариев и не чат, а метки в духе комментариев Figma, только в браузере и в коде. Цель — привлечь внимание к конкретному элементу вместе с контекстом. Прямая отправка участнику похожа на сообщение, но полноценной переписки нет: ни тредов, ни истории диалога. Получатель видит метку на месте и отвечает действием (статус, «Принять → агенту», короткая отметка). Сервер нужен только для того, чтобы участники команды видели друг друга и могли делиться: метками, ссылками, снимками, правками и подборками.

**Обмен — по общему сценарию [P5](#p5-как-работает-обмен--обязательный-сценарий-уточнение-владельца-2026-10-18).** Путь такой: «Поделиться» → получатели (все или конкретные участники) → toast «оставила вам комментарии в …» → открытие на якоре (`seen`) → «Сделано» или «Отклонено» с короткой заметкой (`done`/`dismissed`). Предложение правки (diff/patch) — это ресурс: «Принять» (`accepted`, патч открывается в Review) или «Отклонить» (`declined`).

**Что уже есть:**
- аннотации страниц в preview;
- комментарии к строкам кода в Files viewer (`CodeCommentViewModel`, `MainViewModel.CodeComments.cs`);
- комментарии к hunk в Review.

Всё это сейчас уходит только агенту как часть следующего сообщения.

**Что сделать:**
1. **Единая модель «правки»:**
   ```
   Request { requestId, kind: task|edit|question, author, to: agent|member(memberId)|team(teamId),
             projectId?, anchor: PageAnchor|CodeAnchor|DiffAnchor|DocAnchor, text, attachments[],
             recipientStatus[]: { memberId, status: seen|done|dismissed /* task, question */
                                             | accepted|declined /* edit — ресурс */,
                                  note?: string /* одна короткая отметка ≤280, не тред */ },
             createdAt }
   PageAnchor { url, route, selector, rect, sourceFile?, snapshotId? }
   CodeAnchor { repoFingerprint, path, lineStart, lineEnd, commit, excerpt }
   DiffAnchor { path, hunkHeader, side, line }
   DocAnchor { fileRef, locator /* страница+область или заголовок+фрагмент */, excerpt }
   ```
2. **Режим «Правки»** (переключатель там же, где аннотации, и в Files/Review):
   - точка, область или выделение кода → комментарий;
   - кнопки «Отправить агенту», «Отправить участнику…», «В команду…»;
   - тип: задача / предложение правки (текстом или diff) / вопрос.
3. **Входящие** (GUI и браузер, общие с P5): всё полученное, включая пропущенные toast-ы, с фильтром по проекту, типу и статусу.
   - Открыть метку — встать на якорь: страница со скроллом к элементу, файл на строке или документ на фрагменте. Открытие ставит `seen`.
   - Действия у задачи и вопроса: «Сделано», «Отклонено» — с необязательной короткой отметкой. «Принять → отправить агенту» — локальное действие: якорь и текст превращаются в промпт, статус не меняется.
   - Действия у предложения правки: «Принять» (патч открывается в Review) или «Отклонить». Ответов в треде и переписки нет.
4. **Сдвиг якорей кода.** По `commit` и `excerpt` якорь находится заново, если строки уехали. Если не найден — пометка
   «код изменился» и показ исходного фрагмента.

**Критерии приёмки:**
- Правка со страницы в Nightly доходит участнику в GUI и открывается на том же элементе.
- Правка к строке кода после коммита, сдвинувшего строки, встаёт на правильное место.
- «Принять → агенту» создаёт сообщение с якорем, и агент получает селектор или файл:строки.

**Оценка:** ~1 неделя после P. Отправка агенту без P — 2–3 дня.

**Статус K4:** локальные метки — готово; обмен метками (C2) — готово в GUI: «Отправить…» всем или участникам из меток сообщения (код и страницы), item `mark` по схеме ядра (anchor `code` с `repoFingerprint` и `commit` из git проекта (`RepoIdentity`) или `web`; заметка и полный якорь в `context`), toast «Комментарии от X в …» по автору и объекту, открытие на месте (файл на строке в Files, страница в панели браузера со скроллом к фиолетовой метке), `seen` при открытии, «Сделано»/«Отклонить» с заметкой ≤280, автор видит статус каждого получателя (Team › Комментарии), «В запрос агенту» кладёт полученную метку с якорем в сообщение своему агенту (статус не меняется). Метка кода с другого коммита того же репозитория помечается «строка могла сместиться». Без тредов. Не сделано: автоматический пересчёт якоря по `commit`/`excerpt` (п. 4), предложение правки как ресурс. Код: `ClientCore/Teams/SharedMarks.cs`, `ViewModels/Team/SharedMarksViewModel.cs`, `Views/Team/SharedMarksView`, `SendMarksButton`.

### K7. Встроенный редактор кода · P1

**Новый запрос владельца:** открывать, править и сохранять код с подсветкой синтаксиса. По функциям это редактор,
не второй coding agent. Рекомендован поддерживаемый fork AvaloniaEdit + TextMate и интеграция LSP.

**Упрощение (принцип владельца, 2026-10-18).** Это встроенный open-source редактор, не своя IDE. Обязательно: правка, подсветка, сохранение и сохранность текста при конфликтах. LSP-функции (completion, hover, definition, rename) — только в объёме, который даёт готовый компонент и языковой сервер без отдельной разработки; собственные IDE-функции не наращиваем.

**Объём:** вкладки, document buffers, undo/redo, поиск/замена, dirty/crash recovery, кодировки/BOM/EOL,
folding/multi-caret, completion/hover/diagnostics/definition/rename через LSP, интеграция с K4/Review.
Существующий CodeView — viewer, его не превращать в самописный editing engine.

**Ключевой контракт:** один документ/версия для UI и агента; агент не перезаписывает dirty buffer.
Expected revision/hash, diff/merge при конфликте, атомарное сохранение с контролем внешних изменений.
Неподдерживаемый/слишком большой/binary/read-only файл не должен молча сохраняться обрезанным.

**Приёмка:** реальные edit/save/undo/IME сценарии на трёх ОС; подсветка и LSP на текущей версии документа;
восстановление после crash; конкурирующие правки пользователя/агента/внешнего редактора не теряют текст.
Nightly для редактора не требуется. Совместимость AvaloniaEdit с нашим renderer проверяется до миграции.

**Статус K7:** native editor и document/RPC coordination реализованы; macOS window smoke подтвердил подсветку, Unicode input, undo/redo/save и disk-conflict сохранность. Интеграция: 155 passed / 4 Windows-only skipped; Bun coordination: 18 passed. Реальный language-server/UI, OS IME и Windows/Linux gates ещё не закрыты; подробные доказательства — NEXT_RELEASE_ROADMAP, R0.9.

### K6. Глубокая интеграция omp · P1 (D2 принят)

**Проблема.** Многое в GUI сделано полумерами из-за того, чего нет в RPC omp:
- plan mode;
- lock файла сессии;
- входящий `rpc_chunk`, из-за которого лимит 3 картинки × 230 KB;
- отмена background jobs;
- MCP OAuth;
- разбор текста approval-подсказки (`UNDOCUMENTED / VERSION-PINNED`).

Отдельно: omp 18.8.0 уже отдаёт по RPC больше, чем мы используем (PARITY_ROADMAP §0). Использовать готовые
команды сразу; это не повод откладывать создание форка и исправление недостающих контрактов.

**Принятая политика D2: собственный форк с контролируемыми обновлениями upstream.**
1. Канонические исходники движка находятся в `runtime/engine`, без второй обязательной очереди `patches/`.
   Для публикации форка — upstream remote, рабочая ветка Ombra и неизменяемые release tags; локальное
   импортирование исходников не выдаём за уже созданный удалённый репозиторий или опубликованный release.
2. Новый upstream-тег создаёт кандидат обновления, а не меняет используемый runtime. Смотрим исходный diff,
   переносим изменения в integration-ветке, решаем конфликты и удаляем наши исправления, ставшие избыточными.
   Upstream PR желателен для общих улучшений, но ожидание принятия не блокирует нас.
3. До продвижения кандидата: wire-schema diff, реальные RPC-сценарии, browser/approval/session/job flows,
   упаковка и платформенные проверки. Автоматизация готовит отчёт и кандидат, но не публикует новый runtime сама.
4. GUI пинит собственный артефакт и Bun, upstream base и проверяемый digest полного дерева исходников.
   Fork commit указываем только после его фактического создания. Старые установленные pack не изменяем;
   новый `ombra-engine-18.12.2-bun-1.4.2-v1` активируется только после проверки установки и host-контракта.
5. Один app-owned host обслуживает логические `AgentSession`; процессов CLI/VM/Worker на каждый чат нет.
   RPC мультиплексируется по явному session key, а не текущей вкладке. При cutover удаляем spare/LRU
   process pool и несовместимые обходы. Общий crash требует восстановления ввода всех чатов без auto-send;
   Stop/close отдельной сессии не завершает движок и соседние сессии.

**Первая очередь патчей (кандидаты):**

| Патч | Что даёт GUI | Upstream PR? |
|---|---|---|
| RPC plan mode: enter/exit, событие документа плана, approve/reject + feedback | Plan mode в GUI без терминала | да |
| Lock/lease файла сессии | Нет двух писателей в одной сессии | да |
| Входящий `rpc_chunk` (клиент → omp) | Снимается лимит вложений | да |
| `cancel_job`, `get_job_output` | Stop и вывод фоновых jobs | да |

| Стабильные id и timestamp у всех ролей в `get_messages_page` | Гидрация = живой вид, якоря правок | да |

**Риски.** Частый upstream требует постоянного review, но брать каждый тег не обязательно. Стоимость сопровождения
оцениваем по конфликтам и изменяемым подсистемам, а не искусственному лимиту в 5–7 патчей.

**Оценка:** старт (репозиторий, CI, сборка пакета) 2–3 дня; каждый патч — 1–3 дня; поддержка — постоянно.

## B. Браузер (Nightly)

### B1. Автоматические группы по URL · P1

**Цель.** Когда открыто много однотипных вкладок (пример: 10 вкладок Pinterest с референсами), они сами собираются в
группу, а когда их становится мало — разбираются.

**Что есть в движке.** Нативные группы вкладок Firefox (`gBrowser.addTabGroup`, используется в
`src/zen/sessionstore/ZenWindowSync.sys.mjs`), папки Zen (`src/zen/tabs/ZenPinnedTabManager.mjs`), workspaces Zen.

**Правила:**
- **Ключ группировки** — eTLD+1 (`pinterest.com`, `www.pinterest.ru` → отдельно по eTLD+1) с переопределениями.
  Пользовательское правило «по пути»: например, `github.com/<org>`. Отдельные правила для доменов, где eTLD+1 слишком
  крупный.
- **Порог** собирания — 4 вкладки одного ключа в одном workspace (настраивается: 3–10). Разборка — когда осталось
  меньше 4, с гистерезисом: разбираем при ≤2, чтобы группа не мигала при закрытии и открытии вкладки.
- Группируются только **временные** вкладки. Закреплённые, вкладки в папках Zen и вкладки в группах, созданных
  вручную, не трогаются.
- **Ручные действия побеждают.** Если пользователь вынул вкладку из автогруппы, она больше не попадает туда
  автоматически, пока не закроется. Если переименовал или перекрасил группу, группа становится ручной и не
  разбирается автоматически.
- Имя группы — имя сайта и счётчик. Заголовок — нейтральная строка в стиле Figma Layers, а не яркая цветная плашка; стабильный цвет домена допустим только как ненавязчивый акцент. Chevron, favicon, название и счётчик выровнены по центру одной строки; дочерние вкладки обозначают вложенность отступом.
- Анимация собирания и разборки — короткая (150 мс), с учётом reduced motion.
- Настройки: вкл/выкл, порог, исключения (домены), правила по пути.

**Общая механика с командами кодинг-агента.** Группа — общая сущность платформы:
```
Group { groupId, ownerKind: member|team, ownerId, kind: auto|manual|team, key?, name, color, items[], updatedAt }
GroupItem { url, title, favicon, addedBy, addedAt }
```
- Локальные автогруппы живут только на устройстве: синхронизировать временные вкладки не нужно.
- **Группа команды** — синхронизируемая подборка ссылок (референсы для проекта). Её можно открыть в браузере как
  группу вкладок и увидеть в GUI у проекта команды. «Поделиться группой» идёт по сценарию
  [P5](#p5-как-работает-обмен--обязательный-сценарий-уточнение-владельца-2026-10-18): получатели — все или конкретные
  участники, у получателя toast «поделилась коллекцией "…"». Группа появляется в его браузере только после «Принять»
  (`accepted`); «Отклонить» (`declined`) ничего не добавляет.
- Одна база (P4), поэтому изменения командной группы видны в обоих продуктах.

**Критерии приёмки:**
- 4-я вкладка pinterest.com собирает группу; закрытие до 2 разбирает её.
- Вынутая вручную вкладка не возвращается в группу.
- Переименованная группа не разбирается.
- Клик по заголовку/chevron сворачивает и разворачивает группу; состояние явно видно по chevron. Проверить повторные клики, доступность с клавиатуры и отсутствие случайного переключения вкладки.
- Визуально проверить реальный sidebar на группах GitHub и Pinterest: без ярких заливок заголовка, favicon не выпадает вверх, длинное имя не ломает строку. Ориентир взаимодействия и иерархии — Figma Layers; сравнение с референсом обязательно до UI-приёмки.
- Референс взаимодействия: [Figma — Layers panel](https://help.figma.com/hc/en-us/articles/360039831974-Explore-the-navigation-bar-and-left-sidebar): стрелка у контейнера показывает/скрывает дочерние слои. Для браузерной группы кликабельна также строка заголовка; скрытие списка не закрывает вкладки и не меняет активную страницу.
- Командная группа, изменённая в браузере, видна в GUI у проекта команды.
- Группа, которой поделились, не появляется у получателя до «Принять»; автор видит `accepted`/`declined` по каждому получателю.

**Оценка:** локальная часть 3–5 дней; командные группы — 2–3 дня после P.

### B2. Поделиться URL с комментарием через команды · P2

**Требования:**
- Сценарий — [P5](#p5-как-работает-обмен--обязательный-сценарий-уточнение-владельца-2026-10-18). В меню страницы, вкладки и группы — «Поделиться…» → получатели: все (пространство команды или проекта) или конкретные участники (по ID, из недавних).
- Поля: комментарий (обязательно не пустой или пометка «без комментария»); опционально — выделенный текст,
  скриншот области (из B3), аннотация (K4).
- Доставка через сервис (P), toast получателю в браузере и GUI: «Анна поделилась ссылкой "…"». Пропущенное — во «Входящих» (P5, общие с K4).
- Ссылка — ресурс. «Принять» открывает её во вкладке браузера (`accepted`), а если пришла с аннотацией — сразу на элементе. «Отклонить» (`declined`) убирает карточку. Комментарий отправителя показывается в карточке; ответить можно только статусом с короткой заметкой, без переписки.
- Безопасность:
  - URL с токенами в query показывается с предупреждением «в адресе похоже на секрет»;
  - перед отправкой — очистка через redactor, тот же, что в GUI (`SecretRedactor`).

**Оценка:** 2–3 дня после P.

**Решение (ведущий, 2026-10-18, ради срока).** У Nightly нет собственного устройства команды: «Поделиться» и входящие идут через Ombra на том же Mac по аутентифицированному локальному Mach-каналу с проверкой обеих сторон по audit token (подробно — [SERVER_DESIGN §7](SERVER_DESIGN.md#nightly)). ### B3. Скриншоты — галерея с метаданными, тегами и шифрованием · P1

**Цель.** Скриншот — это не файл в «Загрузках», а элемент галереи с метаданными (где и когда сделан), тегами и
поиском. Ориентир по UX — Eagle.

**Захват:**
- Встроенные скриншоты браузера (компонент `engine/browser/components/screenshots`, `ScreenshotsUtils`): область,
  видимая часть, вся страница, элемент.
- Системные скриншоты, если пользователь включил «Импортировать системные скриншоты»: наблюдение за системной папкой
  скриншотов, импорт в галерею с вопросом «удалить оригинал?». Метаданные в этом случае — время и активная вкладка
  браузера в этот момент, если браузер был на переднем плане [INFERENCE: точность зависит от ОС].
- Drag&drop картинки со страницы в браузер: на время перетаскивания показывать **зону «Сохранить в галерею»** со
  значком. Если в галерее есть папки — показывать их как **чипы со стеклянным эффектом** (backdrop-blur) с названиями;
  drop на чип сохраняет в папку.

**Метаданные (собираются сами):**
```
Shot { shotId, createdAt, source: area|visible|full|element|system|drop,
       url, title, favicon, origin, viewport {w,h,dpr}, scroll {x,y}, selector?, selectionText?,
       pageMeta { ogTitle, ogImage, description, author?, publishedAt? }, colors[] (палитра, 5 цветов),
       tags[], folderId?, note?, width, height, bytes, sha256 }
```
`pageMeta` берётся из `<meta>` и OpenGraph страницы в момент захвата, палитра — квантованием картинки.

**Галерея** (раздел в боковой панели и отдельная страница `about:gallery`):
- сетка masonry, виртуализированная;
- фильтры: теги, папки, сайт, дата, цвет;
- поиск: по тегам, URL и домену, заголовку, заметке, выделенному тексту;
- просмотр: большой режим, метаданные справа, «Открыть страницу» (по URL и scroll), копировать картинку и ссылку;
- массовые действия: теги, папка, удаление;
- автотеги — опционально: домен и тип страницы.

**Шифрование (обязательно):**
- Хранилище — в профиле, файлы зашифрованы AES-256-GCM. Ключ галереи хранится в системном хранилище через
  `OSKeyStore` Firefox (Keychain, DPAPI, libsecret).
- Имена файлов — случайные id, без URL и даты. Индекс (SQLite) с метаданными тоже зашифрован.
- Картинки нельзя открыть или просмотреть через файловый менеджер. Миниатюры — тоже в зашифрованном виде.
  Расшифровка — только в памяти процесса.
- Экспорт — явное действие: «Экспортировать выбранные» в папку, в открытом виде, с подтверждением.
- Опционально: блокировка галереи паролем или биометрией ОС после N минут неактивности.

**Синхронизация.** По умолчанию только локально. Отправка конкретного скриншота участнику или команде — через B2.

**Критерии приёмки:**
- Скриншот области сохраняется в галерее с URL, временем, заголовком и палитрой; находится поиском по тегу и по
  домену.
- Файлы в профиле не открываются никаким просмотрщиком, а их имена не раскрывают сайт.
- Drag картинки показывает зону и чипы папок; drop на чип кладёт картинку в папку.
- Галерея на 5 000 скриншотов открывается за ≤1 с, прокрутка без рывков.

**Оценка:** 1–2 недели.

**Статус B3:** локально сделано на macOS (2026-10-17). Native mochitest `zen/gallery/tests`: **159 passed, 0 failed** (было 85). Зашифрованное хранилище теперь реально проверяется: OSKeyStore, настоящий Keychain, AES-GCM, подмена шифротекста и AAD, отказ при отмене OS-аутентификации и при отсутствии ключа, отсутствие открытого текста в SQLite/WAL. ESLint на путях B3 — 0 ошибок. **Открыто:** Windows/Linux (DPAPI/libsecret, overlay, watch folder); ручная проверка настоящего диалога Touch ID/пароля (не автоматизируется по замыслу); нативный drag&drop на папку.

### B4. Лёгкость и отсутствие непонятных состояний при многих вкладках · P1

**Проблема.** При большом числе вкладок браузер подвисает, и непонятно, грузится что-то или нет.

**Шаг 1 — измерить** (до любых изменений):
- Сценарий: 30 / 60 / 120 вкладок (смесь тяжёлых сайтов, включая Pinterest, YouTube, Figma); холодный старт с
  восстановлением сессии; переключение вкладок; прокрутка вертикального списка вкладок Zen.
- Firefox Profiler (main thread, parent process) плюс `about:processes` и `about:memory`. Записать: время до
  интерактивности, долгие задачи >50 мс, RSS, число content-процессов.
- Сравнить с ванильным Firefox 157 и с Zen upstream. Так станет видно, что внесли наши патчи и UI Zen.
- Повторить одинаковые web-нагрузки в Ombra на том же runtime build: input-to-present p50/p95, frame pacing,
  resize/DPI, idle CPU, суммарная память browser/content/GPU/Ombra и cold/warm start. Отдельно учесть transport
  overhead и совместную работу приложений; сравнение с прежним preview — baseline, не обещание ускорения.

**Шаг 2 — исправления** (по результатам замеров, кандидаты):
- **Ленивое восстановление**: вкладки не грузятся до активации (`browser.sessionstore.restore_on_demand`). Проверить,
  что наши патчи это не ломают.
- **Выгрузка фоновых вкладок**: `TabUnloader` — у нас есть патч `src/browser/components/tabbrowser/TabUnloader-sys-mjs.patch`.
  Выгрузка не только при нехватке памяти, но и после N минут неактивности (настройка). Исключения: звук, формы с
  вводом, закреплённые по выбору.
- **Список вкладок Zen**: виртуализация или удешевление рендера при 100+ вкладках, анимации — только для видимых.
- **Лимит одновременных загрузок** при массовом открытии (например, открыть всю группу): очередь, по 4–6 одновременно.
- Общие tab lifecycle/cache/scheduling оптимизации разместить в runtime/shared services и использовать в обеих
  оболочках. UI-only правки Zen не считать улучшением встроенного браузера Ombra.

**Шаг 3 — явные состояния вкладки** (никаких «непонятно»):

| Состояние | Как показано |
|---|---|
| Грузится | Прогресс-кольцо на favicon; полоса прогресса под адресом с реальным прогрессом, а не бесконечной анимацией |
| Ждёт очереди загрузки | Серое кольцо и tooltip «В очереди: 3» |
| Выгружена | Приглушённая вкладка, tooltip «Выгружена для экономии памяти, загрузится при открытии» |
| Ошибка сети или сертификата | Значок ошибки на вкладке |
| Страница не отвечает | Через 5 с без ответа content-процесса — значок и предложение «Остановить скрипт / Перезагрузить» |
| Процесс упал | Значок и «Перезагрузить» |

**Бюджеты (цели):**
- переключение на загруженную вкладку — ≤50 мс до кадра;
- 120 вкладок при restore-on-demand — холодный старт ≤3 с до интерактивности;
- RSS в простое со 120 вкладками, из которых 10 активных, — не больше, чем у ванильного Firefox +10%;
- нет долгих задач главного потока >200 мс при прокрутке списка вкладок.

**Критерии приёмки:** бюджеты выполнены в сценарии шага 1; каждое состояние воспроизводится и видно;
до/после записаны для standalone и embedded. Регрессия surface transport учитывается отдельно; наличие
одного engine build не заменяет замер. Приёмка встроенного режима зависит от K1.

**Оценка:** ~1 неделя (замеры 1–2 дня + исправления).

**Статус B4:** локально сделано на macOS (2026-10-17). Стенд `tools/perf/tab-baseline/run.py` в репозитории Nightly. Baseline для 120 вкладок: footprint 6,3–6,5 GB, переключение p95 22 ms, прокрутка max 7,8 ms, восстановление ≤ 1,4 s — в бюджете. Реализовано: (1) ленивое массовое открытие с очередью загрузки ≤6 (`zen.tabs.load-queue.*`) и видимым состоянием «в очереди» — пунктирная рамка иконки, приглушённый курсив, подсказка «Ожидает загрузки (N из M)»; (2) `browser.lowMemoryResponseMask=3` на macOS; (3) таймерный выгрузчик неактивных вкладок — 20 мин, не трогает активные, закреплённые, со звуком/PiP/захватом устройств, с введёнными данными; настройки в «Управлении вкладками». Mochitest 37/0, lint 0. Замер на одной сборке, 120 вкладок, чередованием выкл/вкл: freeze при открытии **3,1–3,2 s → 78–82 ms**; все вкладки загружаются примерно на 0,6 s позже; footprint после 300 s простоя без регрессии (6253 против 6295 МБ в среднем). Прирост после 120 s оказался артефактом более поздних загрузок. **Решение владельца:** `webIsolated` 4→1 (−27 % памяти, но вкладки одного сайта делят процесс) не включено. **Открыто:** Windows/Linux; замер во встроенном режиме Ombra после интеграции K1.
