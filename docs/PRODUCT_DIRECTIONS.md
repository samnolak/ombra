# Новые направления: кодинг-агент (OMP GUI / Ombra) и браузер (Nightly Browser)

Живой документ. В нём описано, что делаем, зачем, как и как проверить. Когда работа сделана, исполнитель отписывается
в блоке «Статус» у пункта и в «Журнале» в конце. Паритет с Codex и Claude Code, их исправленные баги и микро-UX
описаны отдельно: [`avalonia/docs/PARITY_ROADMAP.md`](../avalonia/docs/PARITY_ROADMAP.md).

Продукты:
- **Кодинг-агент** — этот репозиторий (`avalonia/`): .NET 10 + Avalonia, omp запускается как `omp --mode rpc-ui` и
  управляется по JSONL RPC через stdio. omp закреплён на версии 18.8.0, лицензия MIT.
- **Браузер** — `~/Documents/ArcLike Browser/desktop`: Nightly Browser, форк Zen Browser на Firefox 157
  (`surfer.json`). Свой код лежит в `src/zen/…` и патчах `src/browser/…`, исходники Firefox — в `engine/`.

С этими доработками продукты становятся связанными: у них общий участник (ID и имя), общие команды, общие группы и
общий обмен ссылками и правками.

Обозначения:
- **ID пунктов:** K — кодинг-агент, B — браузер, P — общая платформа;
- **приоритет:** P1 — основа, на которой стоит остальное; P2 — ценность; P3 — потом;
- **оценка** — грубая прикидка работы вместе с проверкой; не обязательство;
- **[INFERENCE]** — вывод, не проверенный запуском.

## P. Общая платформа: участники, команды, синхронизация

Основа для K2, K4, B1 и B2. Без неё каждый продукт сделает свою модель, и связать их потом будет дороже.

### P1. Участник: ID и имя

**Зачем.** Чтобы собираться в команды и адресовать правки и ссылки конкретному человеку.

**Требования:**
- При первом входе в любом из двух продуктов создаётся **участник**:
  - `memberId` — стабильный, случайный, ULID или UUIDv7, не выводится из почты или железа;
  - `displayName` — обязательное, задаётся пользователем;
  - аватар — опционально, инициалы по умолчанию.
- Один участник — несколько **устройств** и **клиентов** (GUI, браузер): у каждого свой `deviceId` и ключ, привязка
  к участнику через код или QR. Отвязка устройства из настроек.
- ID можно скопировать: «Мой ID» в настройках обоих продуктов, формат для передачи — короткий `ab12-cd34-ef56`
  плюс полный в QR.
- Имя видно в командах, у отправителя ссылки или правки, в прогрессе.
- Без участника оба продукта работают как сейчас, полностью локально. Вход опционален и выключается.

**Данные:**
```
Member  { memberId, displayName, avatar?, createdAt }
Device  { deviceId, memberId, product: gui|browser, publicKey, name, lastSeenAt }
```

**Безопасность.** Ключи устройств лежат в системном хранилище: macOS Keychain, Windows DPAPI/Credential Manager,
libsecret. В браузере — `OSKeyStore` Firefox (модуль есть в `engine`, используется formautofill).

### P2. Команды (рабочие пространства)

**Требования:**
- Любой участник создаёт команду и становится её **владельцем**.
- Владелец:
  - добавляет участников по ID или приглашением (ссылка или код с TTL) и удаляет их;
  - назначает **причастность**: к каким проектам команды участник имеет доступ и с какой ролью — `viewer` (видит
    прогресс), `contributor` (отправляет правки и задачи);
  - **передаёт владение** другому участнику. Передача подтверждается обеими сторонами, старый владелец становится
    обычным участником.
- Участник выходит из команды сам. Владелец выйти не может, пока не передал владение.
- Удаление команды — только владельцем, с подтверждением вводом имени команды.
- **Проект команды** — это привязка локальной папки или репозитория участника к проекту команды. Привязка идёт по
  remote URL git, а при его отсутствии — вручную. Локальный путь на сервер не уходит.

**Данные:**
```
Team        { teamId, name, ownerId, createdAt }
Membership  { teamId, memberId, role: owner|member, addedBy, addedAt }
TeamProject { projectId, teamId, name, repoFingerprint? }      // repoFingerprint = hash(normalized remote URL)
Access      { projectId, memberId, level: viewer|contributor }
Invite      { code, teamId, createdBy, expiresAt, maxUses }
AuditEvent  { teamId, actorId, kind, payload, at }             // добавление, удаление, передача владения, смена доступа
```

**UX:**
- В GUI — раздел «Команды» в сайдбаре: команды, их проекты, участники с точками статуса.
- В браузере — то же в боковой панели. Управление — в настройках обоих продуктов.

### P3. Прогресс по проектам в реальном времени

**Требования:**
- GUI публикует события прогресса сессий, которые относятся к проекту команды. Публикация **opt-in на уровне проекта**:
  - кто работает: участник и устройство;
  - фаза: working / needs input / idle / error;
  - текущий шаг плана (todo);
  - сколько шагов сделано;
  - изменённые файлы — только имена;
  - время последней активности.
- **Не публикуются** без отдельного явного включения: текст промптов и ответов, содержимое файлов, diff.
- Участник команды видит **ленту прогресса, отфильтрованную по проекту** (фильтр по проекту, участнику и статусу).
  Обновление в реальном времени через WebSocket, при обрыве связи — догон с последнего курсора.
- Presence: онлайн / неактивен / офлайн.

**Протокол** (черновик):
```
→ hello {deviceId, sig, cursor}
← snapshot {teams, projects, presence, progress[]}
→ progress.publish {projectId, sessionKey, phase, step, done, total, files[], at}
← progress.event {...}            // всем с доступом к projectId
← membership.changed / access.changed / ownership.transferred
```
`sessionKey` — непрозрачный хеш, а не путь к файлу сессии.

**Источник в GUI.** Фаза и план уже есть в `ConversationState` (Phase, todos), изменённые файлы — в итоге хода
(`TurnEndRowViewModel`). Нужен издатель с debounce около 1 с, который не шлёт ничего, если проект не привязан.

### P4. Общая база и синхронизация между продуктами

**Требования:**
- Сущности, общие для GUI и браузера: участник, команды, проекты команды, **группы** (B1), **отправленные ссылки и
  правки** (B2, K4), теги (B3, если галерею решат синхронизировать).
- Локально у каждого продукта своя реплика (SQLite). Сервер — источник правды для общих сущностей.
- Офлайн-первый подход: изменения пишутся локально и уходят, когда появляется связь.
- Конфликты: last-writer-wins по полю для простых свойств, add-wins для множеств (участники группы, теги).
- Между GUI и браузером на одной машине — тот же сервер. Прямой локальный канал (native messaging или localhost)
  только для управления браузером агентом (K1), не для данных.

**Оценка P1–P4.** MVP: участник, команды, приглашения, передача владения, прогресс, доставка ссылок и правок —
**2–4 недели** после решения D1.

**Статус P:** не начато. Ответственный: —. Ветка: —.

## K. Кодинг-агент

### K1. Наш браузер внутри агента: аннотации и управление · P1

**Цель.** Агент работает в нашем браузере как в своём: открывает, читает, кликает, делает скриншоты. Пользователь
оставляет аннотации, и агент их получает. В правой панели GUI браузер становится полноценным («больше браузер»), а
аннотации сохраняются.

**Что уже есть** (GUI, встроенный preview):
- omp управляет панелью preview через протокол cmux: `ClientCore/AgentBrowserBridge.cs`, `Browser/TernHost`,
  `TernBlock`;
- на macOS — нативный ввод (`Platform/Mac/NativeInput`), диалоги страниц, загрузки, HTTP auth;
- аннотации страниц: точка или область, селектор, источник для React/Vue/Svelte, привязка к маршрутам SPA
  (`PreviewAnnotations.cs`);
- вкладки и размеры устройств.

**Что сделать:**
1. **Бэкенд Nightly для того же протокола cmux.** Агент продолжает говорить с GUI по cmux, а GUI переадресует команды
   в Nightly. Транспорт до Nightly:
   - **WebDriver BiDi**. Remote-агент в `engine/remote` есть, но Firefox больше не поддерживает CDP. Плюс: штатный
     протокол, есть скриншоты, ввод, события сети. Минус: пока он включён, профиль помечен как автоматизируемый.
     Нужно проверить, как это выглядит в Nightly;
   - **или собственный компонент Nightly** (`src/zen/…`) с локальным каналом: unix socket или named pipe, токен из
     файла с правами 0600. Плюс: полный контроль над UX (индикатор «агент управляет вкладкой»). Минус: свой протокол.
   - **Рекомендация:** собственный компонент. Он даёт тот же набор операций, что `TernBlock`, и BiDi внутри браузера
     для ввода там, где это проще.
2. **Аннотации в Nightly:**
   - тот же режим, что в preview: точка или область, комментарий, селектор, URL, маршрут, снимок области;
   - хранение — в боковой панели Nightly «Аннотации» по URL и проекту;
   - отправка — «агенту в чат X» (через GUI) или «участнику / в команду» (K4).
3. **Индикация управления.** Когда агент управляет вкладкой: рамка вкладки, значок агента и кнопка «Остановить агента
   в этой вкладке». Ввод пользователя во время действия агента ставит агента на паузу.
4. **Согласие по сайту** (как в Claude 2.1.288 и 2.1.296). Чтение и скриншоты — без вопроса. Click, type, eval и
   навигация на залогиненных сайтах вне localhost — с карточкой «once / session / always».
5. **Выбор бэкенда.** Settings › General: «Браузер агента: встроенный preview / Nightly». По умолчанию preview, пока
   Nightly не установлен.

**Критерии приёмки:**
- omp открывает страницу в Nightly, читает её, кликает, вводит текст и делает скриншот. Делает это тот же
  `browser`-tool без изменений в omp.
- Аннотация из Nightly приходит в чат GUI с селектором и URL так же, как из preview.
- Пользовательский ввод во время действия агента ставит его на паузу; кнопка «Остановить» работает.
- Переход на чужой домен с вводом спрашивает согласие.

**Риски.** Сборка Firefox-форка занимает часы, поэтому цикл проверки долгий. Для протокола управления нужно
тестовое окружение без полной пересборки, например artifact build.

**Оценка:** 1–2 недели. **Зависит от:** D4.

**Статус K1:** не начато. Ответственный: —. Ветка: —.

### K2. ID участников и команды с прогрессом по проектам · P1

Реализация P1–P3 на стороне GUI.

**Что сделать в GUI:**

### K3. Эмуляция Android и iOS в клиенте · P2

**Цель.** Верстать мобильные приложения без запуска Xcode или Android Studio. Быстро, без «миллиона часов».

**Факты и ограничения:**
- **iOS Simulator есть только на macOS и только в составе инструментов Xcode.** Легального лёгкого способа запускать
  iOS-приложения без них нет. Сделать можно другое: не открывать Xcode и Simulator.app, а держать simulator
  загруженным в фоне и показывать его экран в нашей панели.
- **Android Emulator** работает на всех ОС. Он умеет `-no-window` (headless) и snapshot-загрузку за секунды.
- **Для web, React Native web и Expo web** лёгкий путь уже есть: preview с размерами устройств, user agent на macOS.
  Его нужно добавить в этот раздел как режим по умолчанию.

**Режимы панели «Устройство»:**
1. **Web-устройство** (есть, доработать):
   - рамка устройства;
   - safe area (вырез и home indicator);
   - имитация touch: курсор-кружок, жесты прокрутки;
   - DPR;
   - тёмная тема устройства (`prefers-color-scheme`);
   - поворот.
2. **Android (нативный):**
   - SDK находится сам (`ANDROID_HOME`, стандартные пути). Если его нет — «Установить минимальный набор»:
     cmdline-tools, один system image (arm64 на Apple silicon), примерно 1–2 ГБ;
   - AVD «OMP Phone» создаётся сам, запуск `emulator -avd … -no-window -no-audio -gpu host` со snapshot;
   - экран — видеопоток в нашу панель (протокол scrcpy через adb: H.264 → декодер платформы), ввод мышью и клавиатурой
     через тот же канал;
   - быстрые действия: установить APK из проекта, перезапустить приложение, logcat внизу, поворот, тёмная тема,
     скриншот в галерею (B3);
   - hot reload — средствами фреймворка (Flutter, RN), мы только держим эмулятор тёплым.
3. **iOS (только macOS):**
   - проверка инструментов: `xcode-select -p`, `xcrun simctl list runtimes`. Если чего-то нет — понятная карточка, что
     и как поставить;
   - `xcrun simctl boot <udid>` без Simulator.app. Экран — через `simctl io <udid> recordVideo` или поток кадров
     (`idb`); ввод — через `idb ui tap/swipe/text`, потому что в `simctl` нет ввода;
   - быстрые действия: установить `.app` из build-каталога, `simctl openurl`, переключение appearance
     (`simctl ui appearance`), status bar (`simctl status_bar override`), скриншот в галерею;
   - устройство остаётся загруженным между запусками GUI (опция), поэтому холодный старт происходит один раз.

**Скорость (цели):**
- повторное открытие Android-эмулятора со snapshot — ≤5 с;
- iOS при загруженном simulator — ≤1 с до первого кадра;
- задержка ввода — ≤80 мс;
- CPU в простое, когда панель скрыта, — около 0: поток останавливается, устройство остаётся загруженным.

**Агент.** Инструмент через `set_host_tools` (штатный RPC omp): `device_screenshot`, `device_tap`, `device_type`,
`device_install`, `device_logs`. Агент видит результат своей вёрстки.

**Критерии приёмки:**
- Android: от кнопки до интерактивного экрана в панели ≤30 с при холодном старте и ≤5 с со snapshot; клик и ввод
  работают; APK из проекта ставится одной кнопкой.
- iOS на macOS с установленными инструментами Xcode: экран в панели, тап и ввод работают, Simulator.app не открыт.
- Без SDK: карточка с точным следующим шагом, без падений.

**Оценка:** web-режим 2–3 дня; Android ~1 неделя; iOS 1–2 недели.

**Статус K3:** не начато. Ответственный: —. Ветка: —.

### K4. Запросы и правки через режим аннотаций: в коде и на страницах · P2

**Цель.** Тем же жестом, что аннотация, отправить задачу или правку агенту, участнику или команде.

**Что уже есть:**
- аннотации страниц в preview;
- комментарии к строкам кода в Files viewer (`CodeCommentViewModel`, `MainViewModel.CodeComments.cs`);
- комментарии к hunk в Review.

Всё это сейчас уходит только агенту как часть следующего сообщения.

**Что сделать:**
1. **Единая модель «правки»:**
   ```
   Request { requestId, kind: task|edit|question, author, to: agent|member(memberId)|team(teamId),
             projectId?, anchor: PageAnchor|CodeAnchor|DiffAnchor, text, attachments[], status: open|accepted|done|rejected,
             thread: Reply[], createdAt }
   PageAnchor { url, route, selector, rect, sourceFile?, snapshotId? }
   CodeAnchor { repoFingerprint, path, lineStart, lineEnd, commit, excerpt }
   DiffAnchor { path, hunkHeader, side, line }
   ```
2. **Режим «Правки»** (переключатель там же, где аннотации, и в Files/Review):
   - точка, область или выделение кода → комментарий;
   - кнопки «Отправить агенту», «Отправить участнику…», «В команду…»;
   - тип: задача / предложение правки (текстом или diff) / вопрос.

### K6. Глубокая интеграция omp · P1 (после D2)

**Проблема.** Многое в GUI сделано полумерами из-за того, чего нет в RPC omp:

**Рекомендуемая схема (D2-б, мягкий форк):**
1. Репозиторий `omp` под нашей организацией, ветка `ombra/<версия>` = upstream-тег + очередь патчей (`patches/`),

2. В очередь попадает только то, что upstream не примет или примет нескоро. Остальное — сразу PR в

3. CI:
   - на каждый новый upstream-тег — автоматический rebase очереди;
   - прогон наших real-omp тестов (`avalonia/tests`, `RealOmpCommandTests`, `RealSessionAreaTests`);
   - сборка runtime-пакета (`runtime/packs`).
4. GUI пинит собранный пакет так же, как сейчас (pinned omp + Bun, проверка целостности).
5. Правила проекта в ROADMAP «не форкаем и не патчим» заменить на правило очереди патчей.

**Первая очередь патчей (кандидаты):**

| Патч | Что даёт GUI | Upstream PR? |
|---|---|---|
| RPC plan mode: enter/exit, событие документа плана, approve/reject + feedback | Plan mode в GUI без терминала | да |
| Lock/lease файла сессии | Нет двух писателей в одной сессии | да |

## B. Браузер (Nightly)

### B1. Автоматические группы по URL · P1

**Цель.** Когда открыто много однотипных вкладок (пример: 10 вкладок Pinterest с референсами), они сами собираются в
группу, а когда их становится мало — разбираются.

**Что есть в движке.** Нативные группы вкладок Firefox (`gBrowser.addTabGroup`, используется в
`src/zen/sessionstore/ZenWindowSync.sys.mjs`), папки Zen (`src/zen/tabs/ZenPinnedTabManager.mjs`), workspaces Zen.

**Правила:**
- **Ключ группировки** — eTLD+1 (`pinterest.com`, `www.pinterest.ru` → отдельно по eTLD+1) с переопределениями.
  Пользовательское правило «по пути»: например, `github.com/<org>`. Отдельные правила для доменов, где eTLD+1 слишком
  крупный.
- **Порог** собирания — 4 вкладки одного ключа в одном workspace (настраивается: 3–10). Разборка — когда осталось
  меньше 4, с гистерезисом: разбираем при ≤2, чтобы группа не мигала при закрытии и открытии вкладки.
- Группируются только **временные** вкладки. Закреплённые, вкладки в папках Zen и вкладки в группах, созданных
  вручную, не трогаются.
- **Ручные действия побеждают.** Если пользователь вынул вкладку из автогруппы, она больше не попадает туда
  автоматически, пока не закроется. Если переименовал или перекрасил группу, группа становится ручной и не
  разбирается автоматически.
- Имя группы — имя сайта и счётчик, цвет — из палитры по домену (стабильный). Иконка — favicon сайта.
- Анимация собирания и разборки — короткая (150 мс), с учётом reduced motion.
- Настройки: вкл/выкл, порог, исключения (домены), правила по пути.

**Общая механика с командами кодинг-агента.** Группа — общая сущность платформы:
```
Group { groupId, ownerKind: member|team, ownerId, kind: auto|manual|team, key?, name, color, items[], updatedAt }
GroupItem { url, title, favicon, addedBy, addedAt }
```
- Локальные автогруппы живут только на устройстве: синхронизировать временные вкладки не нужно.
- **Группа команды** — синхронизируемая подборка ссылок (референсы для проекта). Её можно открыть в браузере как
  группу вкладок и увидеть в GUI у проекта команды. «Поделиться группой с командой» превращает локальную группу в
  командную.
- Одна база (P4), поэтому изменения командной группы видны в обоих продуктах.

**Критерии приёмки:**
- 4-я вкладка pinterest.com собирает группу; закрытие до 2 разбирает её.
- Вынутая вручную вкладка не возвращается в группу.
- Переименованная группа не разбирается.
- Командная группа, изменённая в браузере, видна в GUI у проекта команды.

**Оценка:** локальная часть 3–5 дней; командные группы — 2–3 дня после P.

**Статус B1:** не начато. Ответственный: —. Ветка: —.

### B3. Скриншоты — галерея с метаданными, тегами и шифрованием · P1

**Цель.** Скриншот — это не файл в «Загрузках», а элемент галереи с метаданными (где и когда сделан), тегами и
поиском. Ориентир по UX — Eagle.

**Захват:**
- Встроенные скриншоты браузера (компонент `engine/browser/components/screenshots`, `ScreenshotsUtils`): область,
  видимая часть, вся страница, элемент.
- Системные скриншоты, если пользователь включил «Импортировать системные скриншоты»: наблюдение за системной папкой
  скриншотов, импорт в галерею с вопросом «удалить оригинал?». Метаданные в этом случае — время и активная вкладка
  браузера в этот момент, если браузер был на переднем плане [INFERENCE: точность зависит от ОС].
- Drag&drop картинки со страницы в браузер: на время перетаскивания показывать **зону «Сохранить в галерею»** со
  значком. Если в галерее есть папки — показывать их как **чипы со стеклянным эффектом** (backdrop-blur) с названиями;
  drop на чип сохраняет в папку.

**Метаданные (собираются сами):**
```
Shot { shotId, createdAt, source: area|visible|full|element|system|drop,
       url, title, favicon, origin, viewport {w,h,dpr}, scroll {x,y}, selector?, selectionText?,
       pageMeta { ogTitle, ogImage, description, author?, publishedAt? }, colors[] (палитра, 5 цветов),
       tags[], folderId?, note?, width, height, bytes, sha256 }
```
`pageMeta` берётся из `<meta>` и OpenGraph страницы в момент захвата, палитра — квантованием картинки.

**Галерея** (раздел в боковой панели и отдельная страница `about:gallery`):
- сетка masonry, виртуализированная;
- фильтры: теги, папки, сайт, дата, цвет;
- поиск: по тегам, URL и домену, заголовку, заметке, выделенному тексту;
- просмотр: большой режим, метаданные справа, «Открыть страницу» (по URL и scroll), копировать картинку и ссылку;
- массовые действия: теги, папка, удаление;
- автотеги — опционально: домен и тип страницы.

**Шифрование (обязательно):**
- Хранилище — в профиле, файлы зашифрованы AES-256-GCM. Ключ галереи хранится в системном хранилище через
  `OSKeyStore` Firefox (Keychain, DPAPI, libsecret).
- Имена файлов — случайные id, без URL и даты. Индекс (SQLite) с метаданными тоже зашифрован.
- Картинки нельзя открыть или просмотреть через файловый менеджер. Миниатюры — тоже в зашифрованном виде.
  Расшифровка — только в памяти процесса.
- Экспорт — явное действие: «Экспортировать выбранные» в папку, в открытом виде, с подтверждением.
- Опционально: блокировка галереи паролем или биометрией ОС после N минут неактивности.

**Синхронизация.** По умолчанию только локально. Отправка конкретного скриншота участнику или команде — через B2.

**Критерии приёмки:**
- Скриншот области сохраняется в галерее с URL, временем, заголовком и палитрой; находится поиском по тегу и по
  домену.
- Файлы в профиле не открываются никаким просмотрщиком, а их имена не раскрывают сайт.
- Drag картинки показывает зону и чипы папок; drop на чип кладёт картинку в папку.
- Галерея на 5 000 скриншотов открывается за ≤1 с, прокрутка без рывков.

**Оценка:** 1–2 недели.

**Статус B3:** не начато. Ответственный: —. Ветка: —.

### B4. Лёгкость и отсутствие непонятных состояний при многих вкладках · P1

**Проблема.** При большом числе вкладок браузер подвисает, и непонятно, грузится что-то или нет.

**Шаг 1 — измерить** (до любых изменений):
- Сценарий: 30 / 60 / 120 вкладок (смесь тяжёлых сайтов, включая Pinterest, YouTube, Figma); холодный старт с
  восстановлением сессии; переключение вкладок; прокрутка вертикального списка вкладок Zen.
- Firefox Profiler (main thread, parent process) плюс `about:processes` и `about:memory`. Записать: время до
  интерактивности, долгие задачи >50 мс, RSS, число content-процессов.
- Сравнить с ванильным Firefox 157 и с Zen upstream. Так станет видно, что внесли наши патчи и UI Zen.

**Шаг 2 — исправления** (по результатам замеров, кандидаты):
- **Ленивое восстановление**: вкладки не грузятся до активации (`browser.sessionstore.restore_on_demand`). Проверить,
  что наши патчи это не ломают.
- **Выгрузка фоновых вкладок**: `TabUnloader` — у нас есть патч `src/browser/components/tabbrowser/TabUnloader-sys-mjs.patch`.
  Выгрузка не только при нехватке памяти, но и после N минут неактивности (настройка). Исключения: звук, формы с
  вводом, закреплённые по выбору.
- **Список вкладок Zen**: виртуализация или удешевление рендера при 100+ вкладках, анимации — только для видимых.
- **Лимит одновременных загрузок** при массовом открытии (например, открыть всю группу): очередь, по 4–6 одновременно.

**Шаг 3 — явные состояния вкладки** (никаких «непонятно»):

| Состояние | Как показано |
|---|---|
| Грузится | Прогресс-кольцо на favicon; полоса прогресса под адресом с реальным прогрессом, а не бесконечной анимацией |
| Ждёт очереди загрузки | Серое кольцо и tooltip «В очереди: 3» |
| Выгружена | Приглушённая вкладка, tooltip «Выгружена для экономии памяти, загрузится при открытии» |
| Ошибка сети или сертификата | Значок ошибки на вкладке |
| Страница не отвечает | Через 5 с без ответа content-процесса — значок и предложение «Остановить скрипт / Перезагрузить» |
| Процесс упал | Значок и «Перезагрузить» |

**Бюджеты (цели):**
- переключение на загруженную вкладку — ≤50 мс до кадра;
- 120 вкладок при restore-on-demand — холодный старт ≤3 с до интерактивности;
- RSS в простое со 120 вкладками, из которых 10 активных, — не больше, чем у ванильного Firefox +10%;
- нет долгих задач главного потока >200 мс при прокрутке списка вкладок.

**Критерии приёмки:** бюджеты выполнены в сценарии шага 1; каждое состояние из таблицы воспроизводится и видно; замеры
до и после записаны в журнал.

**Оценка:** ~1 неделя (замеры 1–2 дня + исправления).

**Статус B4:** не начато. Ответственный: —. Ветка: —.
