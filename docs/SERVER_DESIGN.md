## 0. Проверенная основа: MLS (RFC 9420) через OpenMLS

Собственный протокол ключей не проектируем. Групповые ключи — **MLS (RFC 9420)**, реализация **OpenMLS 0.9.1 (MIT)**, вызываемая через тонкий Rust-крейт с C ABI. Тот же крейт содержит **единый валидатор** политики (roster, DeviceCertificate, staged commit, Welcome) для Ombra и Nightly (§7, SD-14). Альтернатива без Rust в .NET-стеке с сопоставимой зрелостью не найдена; это решение §11-D-1.

**Probe (проверено запуском 2026-10-17):** `.temp/D1Design/mlsffi` (Rust cdylib: `openmls =0.9.1`, `openmls_rust_crypto =0.6.0`, `openmls_basic_credential =0.6.0`) + `.temp/D1Design/MlsProbe` (.NET 10, `DllImport("mlsffi")`). Воспроизведение: `cd .temp/D1Design/mlsffi && ~/.cargo/bin/cargo build --release`, затем `cd ../MlsProbe && PATH=$HOME/.dotnet:$PATH dotnet run -c Release`. Последний прогон (.NET 10.0.12, macOS 26.6.2 arm64): **ALL CHECKS PASSED (38/38)**.

Политика в probe: каждый commit и Welcome проверяется против roster scope-а, который вызывающий код передаёт как проверенный (строки `deviceId, memberId, role, ключ подписи MLS`; роль `revoked` — отозванное устройство участника), и против ожидаемого roster-хэша в расширении GroupContext `0xF0A1` (объявлено в RequiredCapabilities). Welcome сверяется с версией roster, закреплённой приглашением (`rosterHead`), и со списком допустимых хэшей (head и более поздние). Нарушение даёт rc=-10 (commit) или -12 (Add/Welcome), и состояние не меняется. Упрощение probe: производный roster (отзыв устройства, проекция на проект) сохраняет roster-хэш группы; в проекте хэш меняется GroupContextExtensions в том же commit, что проверено отдельными тестами GCE.

## 1. Репозиторий и эксплуатация

```
server/
  src/Ombra.Server/            ASP.NET Core 10: HTTPS API, WebSocket, delta sync
  src/Ombra.Server.Cli/        ombra-admin: операторский CLI (только сокращение доступа + обслуживание)
  src/Ombra.Server.Contracts/  DTO/wire-контракты (Ombra.ClientCore; JSON schema для Nightly)
  native/ombra-core/           Rust-крейт: OpenMLS + валидатор roster/сертификатов/commit/Welcome, C ABI
  native/ombra-core/vectors/   общие тест-векторы (JSON) для xUnit и xpcshell/mochitest
  migrations/                  Postgres миграции, только forward
  deploy/
    install.sh                 установка одной командой
    compose.yaml               server + postgres (+ caddy в режиме домена)
    ombra-server.service       systemd unit для варианта без Docker
  tests/                       unit, интеграционные (Testcontainers), e2e, «злой DS-прокси» (§9)
```

Сервер не хранит MLS-секреты групп: он хранит и упорядочивает handshake-сообщения и ciphertext. Сервер использует тот же крейт `ombra-core` в режиме «публичная проверка»: подписи Envelope, правила roster (§4.1), заголовки MLS. Это барьер от мусора, не основа безопасности — клиенты проверяют всё сами.

### Установка одной командой

Откуда релизы: workflow `.github/workflows/server-release.yml` (пуш тега `server-v<версия>`) собирает `make-release.sh`, подписывает ключом из секрета `SERVER_RELEASE_SIGNING_KEY` и публикует `ombra-server-<версия>.tar.gz` как prerelease GitHub `server-v<версия>` (никогда не Latest: его читает апдейтер приложения). Публичный ключ — `server/deploy/release.pub`; Ombra ставит закреплённую версию (URL, SHA-256, ключ в `TeamServerRelease.cs`) по SSH со страницы Team.

Основной путь: распаковать подписанный релиз и запустить `server/deploy/install.sh --ip 203.0.113.5` **или** `--domain team.example.com`. `curl | sh` не используем. Скрипт:
1. Проверяет подпись релиза: каждый файл дерева (`bin/`, `deploy/`, `images/`) обязан быть в подписанном `SHA256SUMS`, лишние/неподписанные файлы и симлинки — отказ; архив образа (по умолчанию или `--image-archive`) сначала копируется в root-only временный каталог (0700), SHA-256 копии сверяется с подписанной записью `images/*`, и загружается именно эта копия. Затем Docker/Compose (или ставит systemd-вариант с собственным Postgres; он только для режима IP — `--systemd --domain` отклоняется, Caddy есть только в Docker-варианте). Сам себя `install.sh` проверить не может, поэтому оператор **до запуска** проверяет релиз в его каталоге ключом издателя, полученным вне канала: `openssl dgst -sha256 -verify release.pub -signature SHA256SUMS.sig SHA256SUMS && sha256sum -c SHA256SUMS` (macOS: `shasum -a 256 -c SHA256SUMS`); эту команду печатают `make-release.sh` и `install.sh --help`.
2. Генерирует пароль БД, ключ подписи токенов, `serverId` в `/etc/ombra/` (0600, владелец root). Серверу доступны только читаемые им файлы (`token.key`, `server-id`, `tls/current.*`, `backup-recipients.txt`): Docker монтирует ровно их read-only, а не весь `/etc/ombra`. Перед каждым `compose up/run` (установка, `--upgrade`, откат) `backup-recipients.txt` гарантированно существует как обычный файл (пустой, если получателя нет), чтобы bind-mount не создал на его месте каталог.
3. Режим IP: генерирует **долгоживущий** SPKI-ключ TLS (ECDSA P-256) и **следующий** резервный ключ; печатает SHA-256 отпечатки обоих (§6.2). Резервный ключ сразу пишется в `/etc/ombra-offline/next.key` (root, 0700/0600; не монтируется и недоступен серверу), оператор уносит его с хоста. Режим домена: Caddy с ACME, авто-продление; Kestrel отдаёт plain HTTP только на loopback/внутреннюю сеть.
4. Применяет миграции, запускает сервис, проверяет health-check (неудача — ошибка установки в любом режиме, код не выдаётся), печатает **bootstrap-код** (одноразовый, TTL 1 ч) **вместе с pin** (§2.4).
Наружу только 443 (HTTPS+WSS); Postgres только во внутренней сети.

### Резервные копии и восстановление (SD-08)

- `ombra-admin backup --out <file>`: `pg_dump` + blob-хранилище → архив, зашифрованный ключом оператора (age). **Таблицы `delivery`, `transfers` и ciphertext передач в бэкап не входят** (D-7, R5-11). Вложения входят: это ciphertext, живущий до DELETE/TTL (§3.3). Срок хранения бэкапов задаёт оператор (по умолчанию ротация 14 ежедневных копий); он указан в §8 п.1. Дополнительное шифрование защищает metadata.
- Бэкап **не содержит** клиентских ключей и не восстанавливает содержимое без устройств участников — это свойство.
- **Restore** возвращает старые блокировки и roster, поэтому сервер после restore стартует в режиме **«карантин»**:
  0. до приёма любого `hello` сервер проверяет и применяет внешний `revocations.log` и `blob-deletions.log` (R2-08, N11): копии из `--revocations-log`/`--blob-deletions-log`, иначе настроенные `Ombra:RevocationsSink`/`Ombra:BlobDeletionsSink`. Копия проверяется по хэш-цепочке и не может быть короче журнала, записанного в манифесте бэкапа (иначе это чужая или усечённая копия, restore отклоняется до любых изменений). Отсутствующий файл явной копии или настроенного sink (не смонтирован, опечатка) — отказ, а не «событий не было». Без внешних копий restore **отклоняется**: на новой VM локального журнала нет, и блокировки/удаления после бэкапа молча вернулись бы. Явный отказ — `--no-external-log`: предупреждение оператору и запись `restore.no-external-log` в audit. Таблицы `delivery` и `transfers` очищаются (на случай бэкапа старого формата) — после restore они пусты (R5-11);
  1. ключ подписи токенов перевыпускается — все сессии и refresh-токены недействительны, каждое устройство заново проходит `hello` (§2.2);
  2. доставка контента и выдача blob-ов выключены; принимаются только `hello` и загрузка roster/commit;
  3. при `hello` клиент сообщает свою голову roster и epoch групп и загружает недостающие подписанные RosterUpdate и commit-ы; сервер продлевает цепочку только линейно. Две валидные ветки от общей версии — equivocation (§4.1: альтернатива подписана тем, у кого есть полномочия на её изменения и сейчас, в голове цепочки): команда заморожена до решения owner, **ветка по длине не выбирается** (удалённый до бэкапа админ мог заранее подписать длинную альтернативную ветку). Обе подписанные версии сервер хранит как доказательство (`GET /v1/teams/{id}/roster/equivocation`, `ombra-admin roster equivocation`). **Решение owner** — `EquivocationResolution` (§4.1), подписанное активным устройством owner в голове известной цепочки (по своей заморозке или по доказательству сервера): `POST /v1/teams/{id}/roster/resolution` с любого активного устройства или `ombra-admin roster resolve --team --resolution <файл>` (оператор только передаёт подписанное решение, полномочия — подпись owner). Выбрана известная версия — заморозка снимается; выбрана конфликтующая — версии ≥ v заменяются ею, зеркало roster пересчитывается только в сторону сокращения (роли не повышаются; участники и устройства только отброшенной ветки блокируются, блокировки не снимаются), группы на заменённых версиях закрываются и пересоздаются следующим поколением (§4.1). Отвергнутая версия после этого — `409 roster-conflict`, новой заморозки не вызывает; остальные клиенты берут решение из `GET /v1/teams/{id}/roster/resolutions` и применяют его к своей цепочке. В audit — `roster.equivocation` и `roster.equivocation.resolved`. Источник правды о составе — подписанная цепочка у клиентов, а не журнал сервера;
  4. карантин команды снимает устройство owner, не любой админ; либо явно `ombra-admin quarantine release --team` с предупреждением в audit и баннером у клиентов (сервер принадлежит владельцу, D-3). Тест — S0 (R2-08).
- Удаления через CLI (§5.2) дополнительно пишутся в `revocations.log` — хэш-цепочка записей, копия отправляется вне хоста (параметр `--revocations-sink`, например на другой сервер/S3 с object lock). `ombra-admin replay-revocations` проверяет цепочку и применяет её после restore.
- Каждое удаление blob (`DELETE`, TTL) пишется в `blob-deletions.log` — такую же хэш-цепочку `{blobId, at, by}` с копией вне хоста. При restore сервер до выхода из карантина применяет журнал и удаляет восстановленные из бэкапа blob-ы, удалённые после бэкапа (N11).
- `ombra-admin backup verify` восстанавливает во временную БД и сверяет счётчики.

### Обновления

- `install.sh --upgrade`: проверка подписи релиза и образа (как при установке) → бэкап → миграции (совместимые с N-1 клиентом) → старт → health-check, откат образа при неудаче. Оставшийся от старых релизов `/etc/ombra/tls/next.key` переносится в `/etc/ombra-offline/`, права `/etc/ombra` сужаются до схемы выше.
- Версия протокола в `hello`; поддерживаются текущая и предыдущая мажорная версии клиентов, иначе `426 upgrade-required`.

## 2. Идентичность, устройства, pairing, восстановление

### 2.1. Сущности и ключи

```
Member  { memberId (UUIDv7) }                         // displayName — внутри roster под E2EE (SD-16)
Device  { deviceId (UUIDv7), memberId, product: gui|browser,
          identityKey (Ed25519), mlsSignatureKey, revokedAt? }
DeviceCertificate { serverId, memberId, deviceId, identityKey, mlsSignatureKey,
                    issuerDeviceId, pairingNonce, issuedAt }   // подпись identityKey выдавшего устройства
```
- Ключи генерируются на устройстве и не покидают его. MLS credential = `deviceId`; лист MLS-дерева — устройство.
- **Roster содержит ключи устройств** (§4.1): `{deviceId, H(identityKey), H(mlsSignatureKey)}`. Валидатор сверяет каждый лист Add/Welcome/UpdatePath с этой записью (probe: SD-01/03/04).
- **Хранение (SD-10):** macOS Keychain `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, без синхронизации iCloud; Windows DPAPI (CurrentUser) + CNG; Linux libsecret; Nightly — `OSKeyStore`. Без secure storage вход в команду недоступен (без plaintext fallback). Состояние MLS (ключ подписи, HPKE leaf/init, epoch secrets) и локальная реплика шифруются AES-256-GCM ключом из OS store.
- **Клоны (SD-10):** при установке создаётся `installId` в несинхронизируемом хранилище и записывается внутрь зашифрованного состояния. Несовпадение (профиль восстановлен из Time Machine/образа на другой машине) переводит устройство в состояние «требуется повторный pairing»: ключи перевыпускаются, старое устройство отзывается. Это предотвращает и двойное использование MLS generation.
- **Экспорт:** только plaintext элементов/вложений по явному действию; ключи не экспортируются никогда.
- Короткий ID `ab12-cd34-ef56` — только адрес для поиска, не credential. **Safety number** участника — хэш его identityKey-корня (первого устройства) и ключей текущих устройств; показывается как QR/60 цифр.

### 2.2. Аутентификация на сервере

`hello` содержит подпись identityKey над `(serverId, nonce, deviceId, time)`. Сервер выдаёт access token (15 мин) и refresh, привязанный к устройству; отзыв устройства инвалидирует токены и сокеты. В Git-сценарии (§10) OIDC провайдера (Authorization Code + PKCE) подтверждает личность и права репозитория; ключи содержимого он не выдаёт (§4.4).

### 2.3. Pairing нового устройства (SD-09)

1. Новое устройство генерирует ключи и показывает QR `{deviceId, identityKey, mlsSignatureKey, pairingNonce}` — **полные ключи в QR**, не ссылка на сервер.
2. Старое устройство сканирует QR. Если камеры нет — ручной ввод кода, содержащего **≥128 бит** отпечатка, либо SAS: оба устройства показывают 6 слов, вычисленные из обоих ключей и nonce после обмена через сервер, пользователь подтверждает совпадение. Подставленный сервером ключ даёт разные слова.
3. Старое устройство подписывает DeviceCertificate (со `serverId`, `pairingNonce`, `issuerDeviceId`) и отправляет на сервер.
4. Устройство вносится в roster (RosterUpdate) и добавляется в группы: если участник — админ, сам; иначе Add proposal, commit делает админ. Админ-валидатор принимает только устройство, сертификат которого подписан **неотозванным** устройством того же участника.
5. **Каскадный отзыв:** DeviceRevocation отзывает и все устройства, выданные отзываемым после момента `compromisedSince` (указывается при отзыве; по умолчанию — дата последнего подтверждённого использования). Такие устройства надо подключить заново.

### 2.4. Bootstrap владельца инстанса

Первое устройство вводит bootstrap-код **и pin** из вывода `install.sh` (SD-13) и становится `ServerOwner` — правом **создавать команды** на этом сервере. Это право серверное и не даёт доступа к содержимому. Команду создаёт устройство: оно подписывает genesis roster, `teamId = H(genesis)`. `ombra-admin bootstrap reset` позволяет оператору создавать новые команды, но не подменить существующие: их genesis-хэши уже у участников. Против «команды, созданной оператором» в Git-сценарии — §4.4.

### 2.5. Восстановление

- Потеря одного устройства при наличии другого — отзыв с другого устройства (§5.4).
- **Потеря всех устройств участника:** новое устройство — новый корень. Админ подтверждает его как того же участника только после **обязательной** сверки safety number вне канала (лично/видео). Все члены команды видят событие «ключ Анны изменился» (SD-03). **Пары с этим участником (N9):** у каждого собеседника пара замораживается — новые элементы не отправляются, новые устройства участника в пару не добавляются — пока **сам собеседник** не сверит safety number локально. Подтверждения админа для пары недостаточно.
- Резервной копии элементов на сервере **нет** (D-7, решение владельца): элементы существуют только в локальных репликах устройств, сервер держит лишь очередь доставки. Потеря всех устройств участника = потеря его локальных элементов; новое устройство получает их только переносом от другого своего устройства (§3.2) или через «поделиться элементами» админа (D-4).
- Потеря устройств **владельца**: §5.4 и D-3 (ключ восстановления владельца либо переустановка сервера с новой командой).

## 3. Отображение на MLS: элементы, группы, доступ к прошлым элементам, вложения, приглашения

### 3.0. Что передаётся: элементы, а не переписка (уточнение владельца 2026-10-17)

Сервер нужен только для двух вещей: участники команды **видят друг друга** (состав и presence) и **делятся элементами**. Чата, ленты комментариев, тредов и истории диалогов нет. Комментарий K4/B2 — метка в духе Figma, привязанная к элементу страницы или к коду, с контекстом. Адресная отправка участнику выглядит как сообщение, но ответить на неё можно только своим статусом и короткой заметкой.

```
ItemKey = (authorMemberId, itemId)                                   // R5-04: ключ элемента — пара
Item { key: ItemKey, kind: mark|file|skill|link|snapshot|edit|collection,
       audience: space {scope: teamId|projectId}                     // виден всем с access к scope
               | member {recipientMemberId},                        // R5-10: в копии — только этот получатель
       createdAt, rev,
       anchor?:  web  {url, selector, textQuote, viewport} |
                 code {repoFingerprint, commit, path, range, excerpt} |
                 doc  {fileRef, locator, excerpt},                      // обязателен для mark
       context?: {text ≤ 2000 симв., selection?, blobRefs[]},           // скриншот/патч — вложения §3.3
       payload:  file {name, blobRef, size, sha256} | skill {manifest, blobRef, version, source}
               | link {url} | snapshot {blobRef} | edit {baseCommit, patch, repoFingerprint} | collection {itemKeys[], title? ≤ 200 симв.},
                 // edit: repoFingerprint (sha256 корневых коммитов) и baseCommit подписаны вместе с патчем; Apply только в клон того же репозитория
       deleted?: tombstone }
RecipientStatus { key: ItemKey, recipientMemberId,
                  status: seen|done|dismissed            // mark
                        | seen|accepted|declined,        // file, skill, link, snapshot, edit, collection — ресурсы
                  note? ≤ 280 симв., seq }
```

**Сценарий обмена (уточнение владельца 2026-10-18, [PRODUCT_DIRECTIONS P5](PRODUCT_DIRECTIONS.md#p5-как-работает-обмен--обязательный-сценарий-уточнение-владельца-2026-10-18)).** Отправитель выбирает объект и получателей (`space` или конкретные участники). Получатель видит toast и запись во «Входящих» — это локальная проекция полученных `item.create`; сервер не хранит ни уведомлений, ни списка входящих.
- **Ресурсы** (`file`, `skill`, `link`, `snapshot`, `edit`, `collection`). До `accepted` клиент ничего не добавляет в workspace и не активирует (в частности skill). Вложение (`blobRef`) он скачивает только после «Принять»; до этого показывает метаданные из payload (имя, размер, манифест skill, список файлов). Отдельного карантина нет. `declined` — вложение не скачивается, карточка уходит из активных Входящих.
- **Метки** (`mark`). Открытие на якоре ставит `seen`; затем `done` или `dismissed` с необязательной заметкой.
- **Переходы.** Статусы получателя упорядочены его `seq` (R5-08):
  - `seen` можно ставить один раз, только до финального статуса;
  - у ресурса `accepted` и `declined` финальны — повторная смена отклоняется;
  - у метки `done` и `dismissed` можно менять между собой, побеждает последний по `seq`.
- **Что видит автор.** Сводку и статус каждого получателя с заметкой: копии статусов приходят только ему, в паре «автор–получатель» (таблица ниже).

**Адресация (R5-10).**
- `space` — элемент шифруется в MLS-группе scope (§3.1): команды или проекта.
- Адресная отправка нескольким участникам — это N независимых копий, по одной в **парную группу** «автор–получатель» (§3.1). В каждой копии `audience = member {recipientMemberId}` этого получателя, и он входит в подпись (ниже). Полный список адресатов хранится только у автора; получатель не видит других адресатов.
- `collection` в копии получателя содержит только ключи элементов, которые этот получатель может видеть: `space`-элементы его scope и элементы, адресованные ему. Остальные автор вырезает до отправки.
- Пару «автор–получатель» клиент показывает с составом устройств обоих участников. Лист вне этих двух участников невозможен при валидаторе §3.1; если он всё же обнаружен, группа замораживается как атака.

**Операции** — типизированные E2EE-payload в MLS application message, закрытый список:

| Операция | Кто может | Где |
|---|---|---|
| `item.create` | участник с access к scope (`space`) или участник пары (`member`) | группа scope / пара |
| `item.edit {baseRev, delta}` | только автор (`key.author` = подписант) | там же, где create |
| `item.delete` (tombstone) | автор; для `space`-элемента также админ, если автор не owner и не admin (как правила §4.1) | там же |
| `collection.add/remove {itemKey}` | только автор коллекции | там же |
| `item.status {status, note?}` | только получатель и только о себе; для `space`-элемента — участник с access к scope в **текущем** roster; статус должен быть допустим для `kind` элемента и не нарушать правила переходов (выше) | **только** в паре «автор–получатель», никогда в группе scope |
| `share {shareId, targetMemberId, targetDeviceId, scopes[], count, sha256}` (N3) | в team-группе — админ; получатель при приёме архива требует, чтобы подписант был админом в **его текущем** roster (снятый админ отдать архив уже не может); в personal-группе — только сам участник и только с `target = self` | team-группа или своя personal-группа; в pair и project — отклоняется |
| `seq.head {groupId → lastSeq}` / `seq.skip {from, to}` (N5) | только сам участник о себе | группа, в которой он писал |

Типа «ответ», тредов и вложенных обсуждений нет; новая реплика — это новый элемент.

**Внутренняя подпись операции (R5-03).** Каждая операция, включая status, delete и collection.*, подписана identityKey устройства-подписанта. Канонические байты:
`"ombra/v1/item-op" ‖ 0x00 ‖ teamId[32] ‖ groupDescriptorHash[32] ‖ epoch u64 BE ‖ rosterVersion u64 BE ‖ rosterHash[32] ‖ authorMemberId[16] ‖ signerMemberId[16] ‖ signerDeviceId[16] ‖ opType u8 ‖ itemId[16] ‖ rev u64 BE ‖ seq u64 BE ‖ recipientMemberId[16] (нули для space) ‖ SHA-256(canonical payload)[32]`.

Валидатор `ombra-core` проверяет:
- MLS-отправитель (credential leaf) = `signerDeviceId`, epoch подписи = epoch доставки, `groupDescriptorHash` = дескриптор этой группы;
- **`rosterVersion` = версии epoch (N4).** В живой доставке `rosterVersion` в подписи должен **точно совпадать** с версией, чей хэш стоит в `ombra_roster_hash` GroupContext этого epoch; любое другое значение — отказ. Поэтому устройство, отозванное в версии V, не может подписать с `rosterVersion = V−1` в epoch, где группа уже на V. Подпись сама связывает операцию с версией roster её epoch. Получателю архива §3.2 достаточно проверить подпись, цепочку roster до этой версии и активность устройства в ней — доверять админу, собравшему архив, не нужно. Устройство должно быть активно в этой версии и не отозвано каскадом (`addedInVersion`/`compromisedSince`, R2-10);
- право на операцию по таблице выше;
- для `member`-копии `recipientMemberId` — второй участник пары;
- лимиты (заметка ≤ 280, текст ≤ 2000, операция ≤ 64 КиБ — остальное вложения), `mark` с якорем.

Отклонённая операция не применяется и не попадает в реплику.

**Ключ и авторство (R5-04).** `itemId` — UUIDv7 автора, но элемент идентифицируется парой `(authorMemberId, itemId)`. Поэтому чужой `create` с тем же `itemId` создаёт другой элемент другого автора и не меняет авторство исходного. Повторный `create` с уже известным ключом отклоняется. `edit`/`delete` принимаются, только если подписант — автор ключа (или админ для delete по таблице). Коллекции ссылаются на `itemKey`.

**Порядок и пропуски (R5-08).** У каждого участника свой монотонный счётчик `seq` на группу. Устройства одного участника берут `seq` из общего счётчика, синхронизируемого через личную группу; при конфликте сравнивается пара `(seq, signerDeviceId)`. Сборка состояния не зависит от порядка сервера:
- элемент — по `rev` автора: `edit` применяется только к `baseRev` = текущему, иначе ждёт недостающий `rev`;
- статус получателя — по его `seq`: побеждает статус с наибольшим `seq` этого получателя, поэтому перестановка сервером не меняет итог;
- разрыв `seq` отправителя в группе, не закрытый за 24 ч, показывается как «часть операций от X не доставлена», поэтому отброшенный tombstone или edit становится заметным.

**Маяки и база `seq` (N5).**
- **Голова в каждом сообщении (N5).** Текущая голова `seq` отправителя в этой группе передаётся во **внутреннем зашифрованном заголовке payload** каждой операции, а не в authenticated data MLS. Сервер её не видит и не узнаёт по ней частоту операций участника. Кроме того, раз в 24 ч и при выходе в сеть участник публикует подписанный маяк `seq.head` в каждой группе, где писал за последние 30 дней. Так отброшенная **последняя** операция (например, финальный tombstone) обнаруживается не позже следующего маяка.
- **Молчащий участник (N5).** Если от активного участника группы, писавшего в неё за последние 30 дней, более 48 ч нет ни операции, ни `seq.head`, клиент показывает «нет подтверждения от X более 48 ч — возможна потеря операций». Так сервер не может скрыть пропуски, просто удерживая и маяки.
- **База.** Для нового участника или нового устройства базой считается первый `seq` отправителя, увиденный после собственного добавления в группу. Разрыв до базы не показывается.
- **Зарезервированный, но не отправленный `seq`.** Устройство, взявшее номер из общего счётчика и не отправившее операцию, при следующем выходе в сеть публикует подписанный `seq.skip {from, to}`. Если устройство отозвано, `seq.skip` за его диапазон публикует любое другое устройство того же участника. Закрытый `skip` диапазон разрывом не считается.

**Удаление элемента (R5-05).** По tombstone каждый клиент **стирает** payload, context, ключи вложений и исходные подписанные операции элемента. Остаётся только `(itemKey, rev, tombstoneSig)`, чтобы элемент не «воскрес» при повторной доставке или в архиве §3.2. Вместе с tombstone клиент автора (или админа) отправляет `DELETE /v1/blobs/{id}` для всех вложений элемента (§3.3).

**Новый участник и старые элементы (D-4, R5-12).** `edit`, tombstone, `collection.*` и статус, ссылающиеся на неизвестный клиенту `itemKey`, игнорируются и не создают элемент. `edit` несёт только дельту к `baseRev`, без полного состояния, поэтому правка старого элемента не раскрывает его новичку.

**Presence.** Онлайн/неактивен/офлайн сервер выводит из сокетов — это metadata, которую он видит в любом случае. Прогресс P3 (фаза, шаг) — эфемерный E2EE-payload `presence.progress`; сервер его не хранит и рассылает только онлайн-устройствам группы, не заблокированным на момент рассылки.

**Хранение и сроки (D-7).** Сервер — **очередь доставки, а не архив**:
- таблица `delivery { groupId, senderDeviceId, opId, epoch, ciphertext, pendingDeviceIds[], expiresAt }` с ключом `(groupId, senderDeviceId, opId)`;
- устройство подтверждает приём (`ack`) **после фиксации в реплике** и исчезает из `pendingDeviceIds`; при пустом списке строка удаляется;
- неподтверждённые операции удаляются через 30 дней (настраивается в `ombra-admin config`);
- хранилище элементов — только локальные зашифрованные реплики устройств;
- в бэкап очередь и передачи не входят (§1, R5-11).

**Очередь: дедупликация, гонки, квоты (R5-06).**
- `opId` уникален для каждой копии (N парных копий — N `opId`). Дедупликация — по `(groupId, senderDeviceId, opId)`, поэтому получатель не может «погасить» чужие копии, повторив увиденный `opId`.
- `POST /ops` и транзакция отзыва (§5.1 п.3, §5.2 п.1) сериализуются блокировкой строки группы (`SELECT … FOR UPDATE`) и проверкой access revision. При вставке `pendingDeviceIds` = неблокированные листья текущего epoch; операция с epoch ≠ текущему → `409`.
- `deviceId` уникален навсегда: повтор в JoinRequest/pairing отклоняется, поэтому блокировку старого устройства нельзя «унаследовать».
- `ack`: устройство берётся только из токена, тело — `opId[]`; ack по строке, где устройства нет в pending, — no-op. `sync` и `410`-snapshot отдают только строки, где устройство в pending.
- Квоты: операция ≤ 64 КиБ, rate на устройство (по умолчанию 20 оп/с, всплеск 100). Объём очереди — **на участника-отправителя (N8)**: доля ≤ max(100 МиБ, объём команды / число участников), по умолчанию объём команды 1 ГиБ. При превышении `429` получает только этот отправитель, а сервер вытесняет его **собственные** самые старые недоставленные операции. Чужие операции не вытесняются, и остальная команда продолжает работать.

**Отзыв доступа.** При удалении участника или устройства (§5) сервер в той же транзакции:
- убирает его устройства из `pendingDeviceIds` всех строк (новых доставок нет); строки, ожидающие только его, удаляются;
- прекращает выдачу ему blob-ов, transfers и эфемерных рассылок.

Элементы, адресованные удалённому, автор видит с пометкой «получатель удалён». Статус удалённого больше не принимается. Пары с удалённым закрываются (§5.1 п.2).

### 3.1. Группы

**Дескриптор группы (R5-01).** У каждой группы есть обязательное неизменяемое расширение GroupContext `ombra_group_descriptor` (0xF0A2, объявлено в RequiredCapabilities):
`{type: team|project|pair|personal, teamId, projectId?, members: [memberA, memberB] по возрастанию (pair) | owner: memberId (personal), generation: u32}`.
- `groupId = SHA-256(canonical(descriptor))`; клиент не принимает группу, чей `groupId` не совпадает с дескриптором.
- **Создание и захват пары (N2).**
  - Сервер в режиме публичной проверки `ombra-core` принимает commit-ы pair/personal-группы, в том числе первый, только от устройства участника дескриптора. Handshake — PublicMessage, credential = deviceId, сервер это видит. Третий участник или сам сервер не может «занять» `groupId` пары: клиенты такую группу не примут, а сервер не примет от постороннего первый commit.
  - Если A и B одновременно создали пару, действует первая по порядку сервера; второй получает `409`, отбрасывает свою группу и ждёт Welcome.
  - **Поколения пары (N2a).** При закрытии пары (удаление участника, сброс состояния) `generation` увеличивается, и новая пара получает новый `groupId`; история epoch старой не мешает. **Действующая пара** — с наибольшим `generation`, для которой принят Welcome (или собственная создающая группа, принятая сервером). Приняв Welcome более высокого поколения, клиент закрывает у себя все младшие поколения этой пары. Операции, отправленные в закрытое поколение, клиент отклоняет, а сервер не принимает в очередь (`409 closed-generation`).
  - **`memberId` не переиспользуется (N2b).** Вернувшийся участник получает новый `memberId` по новому приглашению и, значит, новую пару. Валидатор roster (§4.1) отклоняет RosterUpdate, добавляющий `memberId`, который уже встречался в цепочке.
- GroupContextExtensions, меняющие дескриптор, отклоняются всегда.

Виды групп:
- **team** — одна на команду;
- **project** — для проектов с ограниченным доступом (P2 `Access`);
- **pair** — адресная отправка между двумя участниками (все их устройства), создаётся при первой отправке;
- **personal** — только устройства одного участника (перенос, синхронизация `seq`).

GroupContext также содержит `ombra_roster_hash` (0xF0A1).

**Политика staged commit (SD-04, общий валидатор; probe проверял team/project):**
- отправитель — только лист-участник; external commit (NewMemberCommit/ExternalInit) отклоняется всегда; **GroupInfo с external_pub не публикуется**;
- разрешённые proposals: Add, Remove, Update, GroupContextExtensions; PSK, ReInit и прочие отклоняются;
- **допустимые листья по типу группы (R5-01)** — инвариант R2-12 считается от этого множества:
  - team — активные устройства roster;
  - project — активные устройства участников с `access` к проекту;
  - pair — активные устройства **ровно** `memberA ∪ memberB`;
  - personal — активные устройства `owner`.
- **Add:**
  - в team/project коммитит только админ;
  - в pair коммитит только устройство memberA или memberB, и добавляемое устройство тоже принадлежит memberA или memberB;
  - в personal коммитит только устройство owner.

  Админ, не входящий в пару, сделать Add в пару не может; Add его устройства в чужую пару отклоняется инвариантом. KeyPackage каждого Add — устройство из roster с совпадающим ключом.
- **Remove (R5-02):** любой лист группы может удалить лист, который больше **не** входит в допустимые листья группы. Удалить допустимый лист нельзя никому — кроме участника для своих устройств (SD-15), и то лишь после DeviceRevocation в roster. Поэтому в паре A–B после удаления B участник A сам удаляет листы B, без админа.
- GroupContextExtensions:
  - в team/project — только админ;
  - в pair/personal — любой участник группы.

  Изменять можно только `ombra_roster_hash` и только на хэш проверенного roster.
- Update и UpdatePath — credential не меняется, ключ подписи совпадает с roster. Смена ключа устройства — только через новый DeviceCertificate + RosterUpdate, затем UpdatePath.
- После commit roster-хэш GroupContext равен хэшу текущего проверенного roster либо следующего проверенного RosterUpdate.
- **Инвариант листьев (R2-12, проверено probe):** после commit листья ⊆ допустимые листья типа группы. Состояние «roster отозвал устройство, а лист ещё в дереве» — «ожидает ротации» (hold нового контента, §5); «дерево == допустимое множество» — норма; лист вне множества после merge невозможен.
- **Создание группы (N2):** team/project-группу создаёт только устройство с ролью owner/admin; pair/personal — устройство участника дескриптора. Сервер регистрирует группу (`POST /v1/teams/{id}/groups`, «первая выигрывает») только по GroupInfo **epoch 0**, в дереве которой ровно один лист — создатель (он же подписант GroupInfo), лист допустим для дескриптора, а для team/project создатель — owner/admin и в версии roster из GroupContext, и в голове цепочки; загружает её только сам создатель. Иначе детерминированный `groupId` team/project (дескриптор известен всем участникам) мог бы занять любой участник.

**Welcome** принимается, только если:
- дескриптор согласован с `groupId`, и получатель входит в допустимые листья группы;
- для team/project (R2-01, проверено probe): отправитель — устройство-инвитер `a` либо устройство, которое остаётся админом в версии roster **не ниже `rosterHead`** из приглашения; roster-хэш — `rosterHead` или более поздней версии;
- для pair и personal (N10): отправитель — **лист этой группы**, принадлежащий участнику дескриптора (для pair — любому из двух, в том числе собственное другое устройство получателя; для personal — owner). Устройство должно быть активно в roster и, для пары, не находиться под заморозкой N9;
- все листья дерева допустимы, есть свой ожидающий JoinRequest/pairing (для team/project), epoch не старше известного (SD-11).

До первой отправки контента новый участник ждёт свежий heartbeat (§4.1).

**Порядок и wire format.** Commit-ы упорядочивает сервер (первый на epoch N, остальные `409 epoch-conflict`). Application — PrivateMessage; **handshake — PublicMessage**: сервер видит commit-ы, KeyPackage, credential = deviceId, дерево и дескриптор группы (а значит, пары «кто с кем») — §8 (SD-16), D-10.

**Authenticated data (SD-06).** Каждое application message содержит `(rosterVersion, rosterHash, epoch, epoch_authenticator)`. Получатель, увидев более новое состояние, запрашивает его и до догона не отправляет.

### 3.2. Доступ к ранее опубликованным элементам

**Новый участник не видит ранее опубликованные элементы и метки** (D-4, решение владельца): MLS даёт доступ только к операциям с epoch, в который устройство добавлено.

**«Поделиться элементами» (админ → участник, R5-07).**
- **Что можно включить.** Только `space`-элементы тех scope, к которым у получателя есть `access` в **текущем** roster. Адресные (`member`) элементы, в том числе адресованные самому админу, передавать другому участнику нельзя.
- **Как собирается архив.** Клиент админа включает для каждого элемента все его операции (create, edits, collection.*) **и tombstone** — удалённые элементы передаются только как tombstone. Статусы других получателей не включаются.
- **Подписанное событие.** До загрузки админ публикует в командной группе `share {shareId, targetMemberId, targetDeviceId, scopes[], count, sha256(archive)}`, подписанное по формату §3.0 (`opType = share`). Это видимая всем запись о выдаче.
- **Проверки получателя.** Получатель принимает архив, только если видит событие `share` с совпадающим хэшем, он сам — `target`, а подписант — **админ в текущем roster получателя** на момент приёма (N3). Затем он проверяет каждую операцию:
  - подпись по `rosterVersion` из неё и цепочке roster (R5-03);
  - scope ∈ его access;
  - `audience = space`.

  Остальное отклоняется. Tombstone применяется до create того же ключа.

**Перенос на своё устройство.** Участник переносит **свои** элементы, включая адресные, только на собственное новое устройство через личную группу. Событие `share` с `target = self` публикуется в личной группе.

**Передача** — через `/v1/transfers` (§3.3): одноразовая, не резервная копия (D-7).

**Локальная реплика.** Элементы, статусы и вложения зашифрованы, как в B3. Ключ реплики — отдельный для каждой команды в OS key store; при удалении из команды он уничтожается (§5.1 п.6).

### 3.3. Вложения и передачи (SD-12, R5-05, R5-09)

**Шифрование вложений.**
- AES-256-GCM, чанки по 1 МиБ, случайный ключ на вложение, `AAD = attachmentId ‖ index ‖ isFinal ‖ totalChunks`.
- Получатель отдаёт файл приложению/пользователю **только после** проверки последнего чанка и sha256 всего файла; обрезанный поток — ошибка.

**Загрузка и выдача blob.**
- `PUT /v1/blobs/{id}` — в подписанном Envelope со `scope` = `groupId` группы, где опубликован элемент. Для `member`-элемента это **пара**, поэтому blob выдаётся только устройствам двух её участников (R5-05).
- Сервер хранит `uploaderMemberId`, `uploaderDeviceId`, `groupId`, размер.
- Выдача — только через `GET /v1/blobs/{id}` с device token; проверка членства в группе в момент запроса. **Presigned bearer-URL не используются**; при S3-хранилище (D-8) сервер проксирует поток.

**Удаление blob.**
- `DELETE /v1/blobs/{id}` — подписанный Envelope. Право: загрузивший участник (любое его устройство) или админ scope для `space`-blob, **если загрузивший не owner и не admin** — сервер проверяет это по `uploaderMemberId` и проекции roster (N6). Удаление пишется в `blob-deletions.log` (§1, N11).
- Клиент отправляет его вместе с tombstone (§3.0).
- Без удаления blob живёт до TTL — по умолчанию 180 дней без обращений.

**Квоты.** Вложение ≤ 100 МиБ, квота команды.

**Передачи `/v1/transfers` (R5-09).**
- **Создание.** `PUT /v1/transfers/{transferId}` — подписанный Envelope `{transferId, targetDeviceId, size, sha256, totalChunks}`. Право:
  - админ → активное устройство участника команды (для «поделиться»);
  - участник → только свои устройства (перенос).

  Иначе `403`.
- **Квоты.** Размер ≤ 1 ГиБ (не больше квоты команды); не больше одного активного transfer на целевое устройство; rate — 5 передач в час на отправителя.
- **Формат.** Чанки как у вложений: `AAD = transferId ‖ index ‖ isFinal ‖ totalChunks`; проверка последнего чанка и sha256 до применения.
- **Ключевое сообщение.** Идёт в паре (админ–получатель) или в личной группе, подписано по формату §3.0 и содержит `{transferId, targetDeviceId, size, sha256, key}`. Получатель отклоняет transfer, чьи параметры не совпали.
- **«Один раз».** `GET` и `POST /v1/transfers/{id}/ack` разрешены **только токену `targetDeviceId`** (N3); `GET` повторяется (докачка) до ack; после ack или через 24 ч ciphertext удаляется.
- **Отзыв.** Блокировка устройства или участника удаляет все активные transfers, где он **получатель или отправитель** (N3).

### 3.4. Приглашения (SD-01, SD-03)

Ссылка: `ombra://join?s=<endpoint>&pin=<spki-sha256>&t=<genesisHash>&h=<rosterVersion>.<rosterHash>&a=<fingerprint inviter identityKey>&i=<inviteId>#k=<secret>`.

1. Админ создаёт `Invite { inviteId, teamId, rosterHead: {version, hash}, role, expiresAt, maxUses, verifier }`, подписанный его identityKey; `rosterHead` — версия roster на момент создания (R2-01), она же в ссылке (`h`). `k` — 256 бит случайно, **только во фрагменте** ссылки. Из `k`: `k_srv = HKDF-SHA256(k, salt=inviteId, info="ombra/v1/invite/server")`, `k_adm = HKDF-SHA256(k, salt=inviteId, info="ombra/v1/invite/admin")`. Сервер получает только `verifier = SHA-256(k_srv)`.
2. Приглашённый подключается к `s`, проверяя `pin` (режим IP). Получает от сервера Invite и цепочку roster; проверяет, что Invite подписан ключом с отпечатком `a`, цепочка начинается с genesis `t` и **содержит `rosterHead` из ссылки**; более короткий префикс (сервер скрывает поздние версии) — отказ. Проверка идёт по подписанной проекции roster (§4.1, R2-07); имена участников приглашённый получает после вступления.
3. Приглашённый отправляет `JoinRequest { inviteId, memberId, devices:[{deviceId, identityKey, mlsSignatureKey, keyPackage}], proof_srv = k_srv, bind }`. Сервер проверяет `SHA-256(k_srv)` и TTL, но `bind` проверить и подделать не может: `k_adm` у него нет.
   Канонический формат: `bind = HMAC-SHA256(k_adm, "ombra/v1/invite-bind" ‖ 0x00 ‖ inviteId[16] ‖ memberId[16] ‖ u8 n ‖ для каждого устройства по возрастанию deviceId: deviceId[16] ‖ identityKey[32] ‖ mlsSignatureKey[32] ‖ SHA-256(KeyPackage в TLS-кодировке)[32])`. UUID — 16 байт big-endian, ключи Ed25519 — сырые 32 байта.
4. Устройство админа проверяет `bind` до Add. `k_adm` хранится на устройстве, создавшем приглашение, и передаётся другим админ-устройствам только в **админ-группе** (R2-05, срез S3). Подменённый ключ или KeyPackage → `bind` не сходится → Add не делается, админ видит предупреждение «запрос изменён по пути» (тест S3).
5. **Автопринятие** возможно только при валидном `bind` и только для приглашений `maxUses = 1` (персональных). Многоразовые ссылки (`maxUses > 1`) требуют ручного подтверждения каждого запроса со сверкой safety number: общий `k` знают все получатели ссылки, и любой из них мог бы сделать валидный `bind` для чужого ключа.
6. Админ делает Add + RosterUpdate. Приглашённый принимает Welcome только по правилам §3.1. После вступления обе стороны видят safety number с предложением сверить.

Остаточный риск: канал передачи ссылки (мессенджер, почта) — доверенный. Кто перехватил ссылку целиком, тот может вступить вместо адресата (TOFU канала приглашения, §8).

## 4. Роли, ACL, передача владения

### 4.1. Signed roster (SD-03, SD-05)

```
Roster (полная версия, передаётся только в MLS):
  projection {                                             // видна серверу и приглашённому, все правила — по ней
    teamId, version, prevHash, owner: memberId,
    recovery: {ownerRecoveryKey: Ed25519 pub, timeLock: секунды, custodian?: memberId}   // D-3, в genesis
    heartbeatQuorum: k_hb,                                 // §4.1, по умолчанию 2
    pins: [spkiSha256 current, spkiSha256 next],           // режим IP, §6.2
    members: [{memberId, role: owner|admin|member,
               devices:[{deviceId, H(identityKey), H(mlsSignatureKey), certHash, addedInVersion}]}],
    access:  [{projectId, memberId, level: viewer|contributor}],
    pending?: RecoveryProposal | RecoveryKeyChange,          // §4.1 «Восстановление владения»
    cause?: {kind: app|operator, auditId},
    privateCommit = SHA-256(salt[32] ‖ canonical(privatePart)) }
  privatePart { salt, displayName по memberId, имена устройств по deviceId }
RosterUpdate = { projection, signatures: [ {deviceId, sig = Ed25519(identityKey, "ombra/v1/roster" ‖ 0x00 ‖ canonical(projection))} ] }
rosterHash = SHA-256(canonical(projection));  teamId = rosterHash(genesis)
```

**Проекция и E2EE (R2-07).** Подписывается только `projection`; имена в ней представлены одним хэш-коммитментом `privateCommit` с солью. Сервер и приглашённый проверяют подписи и все правила по полям по проекции, не видя имён. `privatePart` идёт в командной группе MLS (новичку — первым payload после Welcome); получатель сверяет его с `privateCommit`, иначе показывает «имена не подтверждены». Каноническая сериализация — детерминированный CBOR (RFC 8949 §4.2.1: сортированные ключи, минимальные длины); тест-векторы S1.

Правила валидатора (общие для клиентов и сервера, §7):
- `prevHash` = rosterHash предыдущей версии; `version` = предыдущая + 1; цепочка начинается с genesis, хэш которого клиент получил вне сервера (ссылка `t`, или собственное создание команды). Приглашённый требует наличие `rosterHead` из ссылки (R2-01).
- Подписант — неотозванное устройство участника, чья роль в **предыдущей** версии разрешает **каждое** изменённое поле:
  - `member` — только свои устройства (добавить с DeviceCertificate, отозвать) и выход из команды;
  - `admin` — участники с ролью `member` и `access`, приглашения, `pins`;
  - `owner` — назначение, понижение и удаление `admin`; `heartbeatQuorum`; передача и замена ключа восстановления (ниже);
  - смена `owner` — с подписью текущего owner по OwnershipOffer (с `prevHash`) **и** подписью получателя (§4.3), либо только через ключ восстановления владельца. **Админы и любой их кворум владельца сменить не могут** (D-3).
- Инварианты: `owner ≠ ∅`, `owner ∈ members`; у каждого устройства валидный сертификат; `memberId` и `deviceId`, однажды удалённые или отозванные в цепочке, повторно не добавляются (N2b).
- **Equivocation:** две разные валидные версии с одним номером (у одного клиента или при сравнении через authenticated data/heartbeat) → команда замораживается, клиент показывает обе подписанные версии как доказательство. Ветка по длине не выбирается. Equivocation засчитывается, только если конфликтующая версия подписана тем, у кого есть **полномочия на её изменения**, причём подписант — неотозванное и не скомпрометированное (R2-10) устройство и в версии-родителе, и **в голове известной цепочки**: (а) роль owner/admin в родителе одна разрешает каждое изменённое поле, и подписант всё ещё owner/admin в голове; (б) для смены owner — подпись проекции старым или новым owner, который всё ещё owner/admin в голове. Альтернатива без таких полномочий (участник меняет `privateCommit`/`cause`, свои устройства, выходит; админ или owner, с тех пор пониженный или удалённый, — в том числе бывший owner с альтернативной парой Offer/Accept) — просто конфликт `roster-conflict`: отклоняется, ничего не замораживает (иначе любой участник или бывший админ/owner мог бы замораживать команду снова и снова).
- **Решение owner (R2-08):** `EquivocationResolution { teamId, version, chosen, rejected, signature: {deviceId, sig} }`, `sig = Ed25519(identityKey, "ombra/v1/equivocation-resolution" ‖ 0x00 ‖ canonical({teamId, version, chosen, rejected}))`, где `chosen`/`rejected` — rosterHash двух записанных версий. Подписывает неотозванное и не скомпрометированное (R2-10) устройство **owner в голове известной цепочки**; если решение переключает ветку, этот же участник обязан быть owner и в голове выбранной ветки (выбрать ветку, отдающую владение другому, нельзя). Валидатор: выбрана известная версия — снять заморозку; выбрана конфликтующая — усечь цепочку до родителя и применить её заново по всем правилам; `memberId`/`deviceId`, встречавшиеся только в отброшенной ветке, остаются «использованными» (N2b переживает переключение). Отвергнутый хэш запоминается: повторная загрузка — `roster-conflict`, не новая заморозка. Если собственная цепочка owner не заморожена (например, у него альтернатива — лишь конфликт), он подписывает решение по доказательству сервера (обе версии из `GET …/roster/equivocation`). `ombra-core`: `roster.resolution_create` (по своей заморозке или по `evidence`), `roster.resolve`. **Подтверждение в клиенте owner:** до подписи `chosen = conflicting` клиент показывает диф двух веток и явно перечисляет, что будет отменено — отзывы устройств, удаления участников, понижения ролей и смены `pins`/`access` из отбрасываемых версий ≥ v (на клиентах они исчезнут; блокировки на сервере останутся), — и подписывает только после явного подтверждения по этому списку.
- **Группы после переключения ветки.** Epoch, привязанный к заменённой версии (rosterVersion ≥ v), продолжить нельзя: такие группы закрываются у клиентов (`roster.resolve`) и на сервере (`closed_at`; операции и commit-ы → `409 closed-generation`), и создатель пересоздаёт их **следующим поколением** (`generation + 1` в дескрипторе, новый `groupId`) на канонической цепочке. Группы на версиях < v не затрагиваются. Зеркало roster на сервере при переключении только сокращает: роли не повышаются, устройства и участники только отброшенной ветки блокируются.

**Восстановление владения (R2-03, D-3 — решение владельца).** Сервер и команда принадлежат владельцу. Единственный путь сменить владельца без его устройства — **офлайн-ключ восстановления владельца**; без этого ключа — только переустановка сервера и новая команда. Кворума админов нет.
1. **Создание.** При создании команды устройство владельца генерирует `ownerRecoveryKey` (Ed25519), показывает его как 24 слова/файл для печати и требует подтвердить сохранение; в genesis попадает только публичный ключ. Приватная часть на устройствах и на сервере не хранится.
2. **Использование.** `RecoveryProposal { teamId, baseVersion, basePrevHash, newOwner, newOwnerDevice, notBefore = time + timeLock }`, подписанный ключом восстановления, публикуется как RosterUpdate с полем `pending`. Все клиенты сразу показывают «Ключом восстановления запрошена смена владельца на X, применится после <дата>»; владелец получает уведомление на все устройства.
3. **Вето.** До `notBefore` (по умолчанию 72 ч, минимум 24 ч, задаётся в genesis) любое устройство текущего owner подписывает `Veto(proposalHash)` — proposal аннулирован. После `notBefore` без вето любой участник публикует применяющий RosterUpdate; время проверяется по подписанным heartbeat (не по часам сервера). Так кража бумажного ключа заметна и останавливается, пока владелец доступен.
4. **Передача преемнику (явная, видимая команде).** Владелец выбирает «Передать ключ восстановления» → указывает участника-преемника → клиент владельца требует ввести текущий ключ восстановления (подтверждение, что он у владельца), генерирует **новый** ключ, передаёт его приватную часть преемнику зашифрованным сообщением в их личной MLS-группе (или выдаёт для печати, если передача офлайн) и публикует `RecoveryKeyChange { newRecoveryPub, custodian: memberId, signatures: [owner device, old recovery key] }`. Все участники видят «Ключ восстановления владельца передан X». Старый ключ после этого недействителен. Замена ключа без смены хранителя — тот же поток без `custodian`.
5. **Без ключа.** Если владелец потерял все устройства и ключ восстановления (или уволен и ключ не передан), команду восстановить нельзя: оператор переустанавливает сервер (или создаёт новую команду), владелец-преемник создаёт **новый genesis**, участники приглашаются заново. Ранее опубликованные элементы остаются только в локальных репликах участников и в новую команду автоматически не переносятся (старый roster не может доверенно подтвердить нового владельца). Клиенты показывают старую команду как «архив, только чтение».
6. Честно: ключ восстановления — мастер-ключ владения; его кража при недоступном владельце (дольше `timeLock`) даёт захват владения. Враждебный уволенный владелец, не передавший ключ, оставляет команду без пути восстановления — по решению владельца выход только переустановка/новая команда.

**Heartbeat (SD-06, R2-02).** Каждое устройство owner и admin раз в 24 ч и сразу после каждого удаления публикует подписанный heartbeat в командную группу и на сервер. Канонический формат подписываемых байтов:
`"ombra/v1/heartbeat" ‖ 0x00 ‖ teamId[32] ‖ rosterVersion u64 BE ‖ rosterHash[32] ‖ u16 n ‖ для каждой группы по возрастанию groupId: u16 len ‖ groupId ‖ epoch u64 BE ‖ epochProof[32] ‖ time u64 BE (Unix-секунды) ‖ signerDeviceId[16]`, где `epochProof = MLS-Exporter("ombra/v1/heartbeat", teamId ‖ time, 32)` в этом epoch; подпись Ed25519 ключом identityKey.
Правила приёма (валидатор `ombra-core`):
- heartbeat учитывается, только если его `rosterVersion` ≥ версии, которую клиент уже видел, а `epochProof` совпадает с собственным вычислением клиента для того же epoch (heartbeat из чужой ветки/epoch не проверяется и не засчитывается);
- состояние «подтверждено» — если за последние T есть heartbeat от **устройства owner** либо от **k_hb различных memberId** с ролью admin в этой версии (`heartbeatQuorum`, по умолчанию 2, если админов ≥ 2). Один удалённый админ X сам по себе не может держать изолированного клиента «подтверждённым»: его подписи — один голос;
- без подтверждения дольше T (по умолчанию 72 ч) клиент показывает «состояние команды не подтверждено» и прекращает отправку контента;
- остаточный риск: если удалённый — **owner** или единственный админ при `k_hb = 1`, изоляцию нельзя обнаружить до сверки safety number (§8 п.4, D-3).
- Заявления о более новом состоянии в authenticated data (R2-13) блокируют отправку только при подтверждении heartbeat по этому же правилу (срез S5).

### 4.2. Серверный ACL (сокращающий)

Сервер хранит проекцию roster плюс блокировки `Block { memberId|deviceId, teamId, by: operator|admin, at, reason, auditId }`. Право на сервере = `roster разрешает И нет блокировки`. ACL, invitations, revoke — серверные транзакции с revision per scope (ARCH §4), не LWW.

### 4.3. Передача владения

`OwnershipOffer {teamId, from, to, rosterVersion, prevHash, newRoleOfFrom, expiresAt}` подписывает текущий owner → получатель подписывает `Accept` → RosterUpdate с обеими подписями. Сервер принимает его compare-and-swap по `rosterVersion`/`prevHash`. Клиенты принимают только при обеих подписях и совпадении `prevHash`. Если владелец подписал два Offer и сервер их разослал разным клиентам, это equivocation (§4.1) и обнаруживается. Owner не может выйти или удалиться без передачи.

### 4.4. Git-сценарий (SD-02)

> **Вне релиза (решение владельца, 2026-10-18).** Команды — только собственные: участник с ID и именем, создатель — владелец, владелец добавляет и удаляет участников, владение передаётся (PRODUCT_DIRECTIONS P1/P2). Git-провайдер как источник личности, состава и прав команды в этом релизе не делается. Раздел, срез S8, строки матрицы SD-02 и R2-04 сохранены как задел и в приёмку релиза не входят.

- **Связь «аккаунт провайдера ↔ ключ устройства»:** клиент приглашаемого получает у провайдера подписанное доказательство:
  - OIDC `id_token` с `nonce = H(identityKey ‖ teamId)` там, где провайдер его выдаёт (GitLab, Gitea/Forgejo, Azure DevOps, generic OIDC). Админ-устройство само проверяет подпись по JWKS провайдера, `iss`/`aud`/`sub`;
  - для GitHub (OAuth без id_token для пользователей) — подписанный артефакт в самом провайдере: публичный gist/коммит в профиле с отпечатком identityKey, который админ-устройство читает своим токеном. Подписи коммитов не используются как связь, если их ключ не совпадает.
  - Без доказательства автоматический Add **запрещён**; нужна ручная сверка safety number.
- **Кто администрирует команду репозитория:** команду создаёт устройство первого участника с правами admin/maintain в репозитории (проверено его токеном), не сервер. Прежде чем вступить и отправлять контент, клиент **своим токеном** проверяет, что owner и admins команды — admin/maintain в репозитории, а genesis подписан одним из них. Команда, созданная оператором для чужого репозитория, отклоняется (тест S8). Если у клиента нет прав перечислить админов репозитория, он показывает это явно и требует сверки safety number владельца.
- Сервер проверяет доступ у провайдера при операциях (кэш ≤15 мин; недоступность провайдера дольше TTL — доступ приостанавливается). Потеря прав у провайдера = серверная блокировка + ротация по правилам §5.2. Ответ сервера «у него есть доступ» основанием для Add не является.

## 5. Удаление участников и устройств

### 5.1. Из приложения (админ)

1. Админ выбирает участника → «Удалить».
2. Клиент админа публикует RosterUpdate без участника (`cause: app`) и MLS Remove всех его устройств в **team- и project-группах**. **Пары и личные группы (R5-02):** админ в них не входит, поэтому каждый клиент, увидевший новый roster, сам удаляет листы удалённого из своих пар с ним (политика §3.1: любой лист удаляет недопустимый лист). После этого клиент закрывает пару («получатель удалён»), больше в неё не отправляет и стирает её групповое состояние. Личные группы удалённого после блокировки сервером никому не доставляются и стираются при локальной очистке. Commit несёт новый roster-хэш.
3. Сервер в одной транзакции: применяет roster, ставит блокировку, повышает access revision, закрывает сокеты/подписки, удаляет его очереди доставки, запрещает выдачу blob-ов **и одноразовых передач элементов**, отвечает `403 removed` на все запросы. С этого момента удалённый не получает от сервера ни одного байта команды — ни новых, ни ранее опубликованных элементов (D-5).
4. Устройства применяют commit → новый epoch (probe: `UseAfterEviction`/`WrongEpoch`).
5. **Задержка commit сервером (SD-06):** клиент, который видит в authenticated data входящих операций или в heartbeat новый `rosterHash`/epoch, которого у него нет, запрашивает его и не отправляет до догона. Клиент, у которого roster уже удалил X, а X ещё лист в дереве группы, держит новые элементы в outbox («ожидает ротации»), как в §5.2. Полностью изолированный клиент (сервер не доставляет ему ничего нового) защищён только heartbeat-таймаутом T — остаточный риск в §8.
6. **Локальная очистка у удалённого (D-5, best-effort).** Админ-устройство вместе с commit публикует подписанное `RemovalNotice { teamId, memberId, rosterVersion, time }` (подпись identityKey админа; сервер хранит его и отдаёт удалённому на любой запрос). Честный клиент удалённого участника, узнав об удалении любым из путей — MLS-commit с собственным Remove (`self_removed`), проверенный `RemovalNotice` по известному ему roster, либо `403 removed` от сервера команды, — немедленно закрывает команду и **стирает локальные данные команды**: все элементы (метки с якорями и контекстом, ссылки, снимки, правки, коллекции), статусы получателей, вложения и их ключи, MLS-состояние и ключи групп, реплику, кэш миниатюр/поиска, outbox; ключ шифрования локальной реплики команды уничтожается в OS key store (crypto-shred), поэтому остатки в WAL/свободных страницах нечитаемы. Пользователь видит «Вас удалили из команды X; данные команды удалены с этого устройства». Явно экспортированные пользователем копии и файлы вне хранилища приложения не трогаются. Остаточный риск (§8 п.2): изменённый клиент, отключённый от сети, или копии/скриншоты, сделанные заранее, отозвать невозможно; злонамеренный оператор может вызвать очистку ложным `403` — это лишь потеря локальной копии у участника, сервер принадлежит владельцу (D-3).

### 5.2. Через CLI сервера (оператор, SD-07)

`ombra-admin member remove --team <id> --member <memberId|shortId> [--reason …]` (также `device revoke`, `sessions revoke`):
1. Сразу: блокировка, отзыв токенов, закрытие сокетов, удаление устройств удалённого из очереди `delivery`, запрет blob-ов, **transfers и эфемерных рассылок** (R5-12), запись в audit и `revocations.log`. С этого момента сервер ничего не доставляет удалённому.
2. Сервер ставит `PendingRotation {teamId, groups[], blockedMemberId, auditId}`, уведомляет админ-устройства и всех членов команды.
3. Клиенты команды видят «Оператор сервера заблокировал X, ожидает ротации ключей» и **держат новый контент в outbox** до ротации (D-5, решение владельца). Чтение и локальная работа доступны. Удалённый сразу получает `403 removed` и выполняет локальную очистку (§5.1 п.6).
4. Ротация — RosterUpdate с `cause: {kind: operator, auditId}` + Remove в team/project-группах (админ-устройство); пары с удалённым ротирует второй участник каждой пары сам (§5.1 п.2):
   - заблокирован **member** — любое онлайн-устройство админа выполняет её **автоматически** и показывает: «Ротация выполнена по удалению оператором»;
   - заблокирован **admin** — нужно явное подтверждение другого админа или владельца (сервер может прислать фальшивый PendingRotation, а подпись админа не должна молча приписать ему удаление со-админа; тест S5);
   - заблокирован **owner**: сменить его может только держатель ключа восстановления владельца (§4.1, с `timeLock` и вето). Без ключа — сервер переустанавливается и создаётся новая команда (D-3); до этого команда в явном состоянии **«заморожена»**: элементы видны, новые не публикуются.
5. CLI не может отменить удаление и не может вернуть доступ: только новое приглашение от админа.
6. Члены команды видят в истории roster, что инициатор — оператор (`cause`), а подписант ротации — админ.

### 5.3. Удалённый участник offline

При выходе в сеть получает `403 removed` на `hello` (и `RemovalNotice`). Outbox: каждая операция получает `forbidden` и **удаляется из очереди** с пометкой «не отправлено: доступ отозван» (не бесконечный retry). Затем клиент выполняет локальную очистку данных команды (§5.1 п.6). Старый epoch клиенты отвергают (`WrongEpoch`, probe).

### 5.4. Потерянное устройство

- **Обычное устройство (SD-15):** с любого другого устройства участника — «Отвязать» → DeviceRevocation в roster + **Remove своего же листа участником сам** (политика это разрешает, probe проверил), без ожидания админа. Сервер блокирует устройство сразу. Каскадный отзыв — §2.3.
- Если у участника не осталось устройств — админ удаляет устройство (§5.1), до commit действует hold как в §5.2.
- **Устройство админа:** другое устройство того же админа или другой админ/owner. **Устройство владельца:** другое устройство владельца; если устройств не осталось — ключ восстановления (§4.1), иначе переустановка сервера и новая команда (D-3). При создании команды клиент настойчиво предлагает второе устройство владельца и сохранение ключа восстановления.

## 6. Wire-контракты

### 6.1. API

HTTPS (TLS 1.3) + WSS на одном порту. JSON для управления, `application/mls-message` для MLS/ciphertext. Каждая изменяющая операция — подписанный Envelope:

```
Envelope { v:1, opId (UUIDv7), deviceId, scope: teamId|projectId, baseRevision, kind, body, ts }
signature = Ed25519(identityKey, canonical(Envelope))   // заголовок X-Ombra-Sig
```
Сервер дедуплицирует Envelope по `(deviceId, opId)`, операции очереди — по `(groupId, senderDeviceId, opId)` (R5-06), и возвращает сохранённый результат.

| Метод | Назначение |
|---|---|
| `POST /v1/session/hello` | challenge-response, версия, голова roster/epoch (карантин §1) → токены |
| `POST /v1/devices/pair` / `…/certificate` / `…/revoke` | pairing-канал SAS, DeviceCertificate, DeviceRevocation |
| `POST /v1/keypackages` / `GET /v1/keypackages/{deviceId}` | загрузка / выдача KeyPackage **только тем, кто вправе сделать Add по §3.1 (N1)**: админ — для team/project; участник — для устройств собеседника в паре (оба активны в roster, пара не заморожена) и для своих устройств. Лимит — 1 **успешно использованный** KP на пару `(запрашивающее устройство, целевое устройство)` за 24 ч: KP считается израсходованным, только когда сервер принял commit с Add этого KP. После `409 epoch-conflict` или отклонённого commit повторный запрос разрешён. Rate — 30 выдач в час на запрашивающее устройство. Last-resort KP выдаётся только админам; не-админ при пустом запасе получает `404` и ждёт пополнения |

| `GET /v1/teams/{id}/roster/equivocation` / `POST …/roster/resolution` / `GET …/roster/resolutions` | обе подписанные версии открытой equivocation / решение owner `EquivocationResolution` (снимает заморозку, §1 карантин п.3, §4.1) / применённые решения для остальных клиентов |
| `POST /v1/teams/{id}/groups` | регистрация группы по GroupInfo epoch 0 её создателя (§3.1 «Создание группы»), первая выигрывает |
| `POST /v1/teams/{id}/heartbeat` | подписанный heartbeat админа |
| `POST /v1/groups/{gid}/commit` | commit + welcome[] + rosterVersion; 409 при конфликте epoch |

| `POST /v1/groups/{gid}/ops/ack` | подтверждение приёма `opId[]`; **устройство — только из токена**; ack по строке, где устройства нет в pending, — no-op; при пустом `pendingDeviceIds` строка удаляется (N7) |
| `GET /v1/sync?cursor=` | delta: commit-ы, **только строки очереди, где это устройство в pending**, roster, блокировки, pending; `410` → snapshot roster + те же строки (N7) |
| `PUT /v1/transfers/{id}` / `GET …` / `POST …/ack` | одноразовая передача §3.3: создание — подписанный Envelope `{transferId, targetDeviceId, size, sha256, totalChunks}` (админ → устройство участника, участник → свои устройства); GET и ack — только токен `targetDeviceId`, докачка до ack; после ack или 24 ч удаляется; блокировка отправителя или получателя удаляет передачу |

Presence идёт отдельной очередью и не вытесняет `revision`/`removed`; смена своего состояния ограничена на соединение (по умолчанию всплеск 5, затем 1 за 2 с; превышение закрывает сокет `rate-limited`). Доступ открытых сокетов перепроверяется сразу после регистрации, после переподключения LISTEN и периодически (30 с): блокировка закрывает сокет и без NOTIFY; устройство, ещё не входящее ни в одну команду (bootstrap owner, ожидающий вступления), остаётся подключённым с пустым списком команд |

Ошибки: `403 {reason: removed|revoked|blocked|not-admin|quarantine|frozen}`, `409 {reason: epoch-conflict|roster-conflict|equivocation|revision}`, `410 cursor-expired`, `413 too-large`, `426 upgrade-required`, `429 rate-limited`.

**Лимиты до аутентификации и тела запросов.** Тело ограничивается по маршруту до чтения: `/session/*` и `/bootstrap` — 16 КиБ, по умолчанию (Envelope ≤ 96 КиБ, ack и т. п.) — 128 КиБ, handshake (`commit`, `keypackages`, roster, genesis, GroupInfo) — 4 МиБ, и только потоковые `PUT /v1/blobs` и чанки transfers — свои лимиты (§3.3); превышение — `413` до буферизации. `/session/*`, `/bootstrap`, `/invites/*`, `/stream` — rate limit по адресу клиента (по умолчанию 60 в минуту; в режиме домена адрес из `X-Forwarded-For` Caddy). Невостребованных challenge — не больше 5 на deviceId и 100 000 всего (`429`); ожидающих auth-кадра WebSocket — не больше 256 (`503`).

**KeyPackage (SD-11):** lifetime не более 30 дней; админ-устройство проверяет lifetime, наличие устройства в текущем roster и отсутствие отзыва. Last-resort KP допустим, только если обычных нет, и после Add требует обязательного UpdatePath от добавленного устройства (до него — пометка «слабая forward secrecy»).

### 6.2. TLS в режиме IP (SD-13)

- Pin — SHA-256 **SPKI**, а не сертификата: сертификат можно перевыпускать с тем же ключом, не трогая pin.
- В roster закреплены два SPKI: текущий и следующий резервный (ключ сгенерирован при установке, хранится у оператора offline). Смена ключа: `ombra-admin tls rotate --to-next` → сервер предъявляет следующий ключ; админ заранее публикует RosterUpdate с новой парой `{next, new-next}`.
- Без SNI сервер предъявляет один сертификат, поэтому «предъявлять оба» нельзя: клиент сам принимает любой из двух SPKI из roster.
- Компрометация текущего ключа: переход на `next`, админ удаляет скомпрометированный SPKI из roster. Клиент, офлайн дольше обоих переходов, не может подключиться и требует **новую ссылку от админа** (это осознанно: «доверять любому» нет).
- Несовпадение pin — отказ без кнопки «продолжить». Режим домена: обычная проверка цепочки.

### Nightly

**Решение (ведущий, 2026-10-18, ради срока): в этом релизе у Nightly нет собственного устройства команды.** Nightly делится и получает через Ombra, запущенную на том же Mac, — её устройство и есть устройство пользователя на этой машине. Прежняя схема (Rust-компонент `ombra-core` в Gecko через XPCOM, D-6, своя реплика и pairing Nightly как отдельного устройства, срез S7) отложена; без запущенной Ombra Nightly с командой не работает.

- **Канал.** Ombra регистрирует Mach bootstrap-сервис `com.ombra.nightly-teams` в пространстве имён пользователя (`avalonia/src/Ombra.App/Nightly/NightlyTeamLink.cs`). Запрос — обычное Mach-сообщение (заголовок, `u32 version, u32 length`, JSON UTF-8) с send-once правом для ответа; Nightly ждёт ответ в ChromeWorker (`src/zen/teams/ZenTeamLinkWorker.js`, js-ctypes), главный поток не блокируется. Это тот же механизм, что у встроенного канала K1, но без запуска Nightly из Ombra.
- **Проверка сторон (Mach peer check по audit token ядра).** Nightly принимает ответ, только если отправитель — тот же пользователь и проходит code requirement Ombra (`zen.embed.peer-requirement` при Developer ID, иначе `cdhash H"…"` из `zen.embed.peer-cdhash`, который Ombra пишет в профиль своего runtime; как у embed-канала; `zen.embed.allow-unsigned-peer` — только для разработки). Ombra отвечает, только если отправитель — тот же пользователь, его исполняемый файл — известный Ombra Nightly (runtime из поставки, `OMBRA_NIGHTLY_APP`, `/Applications/Nightly.app`) и cdhash его кода равен `cdhash` закреплённого манифеста `runtime/nightly/nightly-runtime.json` (`SecCodeCheckValidity` с требованием `cdhash H"…"`; пропуск — только при `OMBRA_NIGHTLY_ALLOW_UNSIGNED=1`). Чужому процессу Ombra не отвечает: send-once право уничтожается, Nightly видит «Ombra не отвечает». Подробнее — SECURITY.md › Ombra ↔ Nightly trust.
- **Операции** (`NightlyTeamShare`): `state` (готовность и причина: `not-running`, `untrusted`, `signed-out`, `no-team`, `not-ready`, `no-members`; команды и участники с именами из roster Ombra), `share` (страница → `link`, группа вкладок, в том числе автогруппа B1 → `collection`, скриншот из галереи B3 → `file` image/jpeg ≤ 48 КиБ; получатели «все остальные участники» или выбранные; комментарий ≤ 280), `inbox` (long poll: новые адресованные этому участнику ресурсы, ещё без `accepted`/`declined`), `open` (= «Принять» по P5, возвращает ссылку, вкладки группы или изображение), `decline`. Содержимое элементов строит только `TeamShare` (схемы ядра закрытые); отправка — `ITeamItems` Ombra, то есть те же MLS-группы пар, outbox и статусы, что у GUI.
- **UI Nightly** (`src/zen/teams/`): «Поделиться страницей / вкладкой / группой вкладок с командой…» в контекстных меню страницы и вкладки, «Share with team…» в просмотре галереи; диалог — что отправляется, комментарий, команда, «Все» или выбранные участники. Пока Ombra не может делиться, пункты выключены, а под ними написано почему. Входящее — toast «Анна поделилась ссылкой / коллекцией / снимком "…"» с кнопкой «Открыть»: ссылка — вкладка, коллекция — группа вкладок, снимок — изображение во вкладке. Объявленное запоминается (`zen.teams.inbox-after`/`-skip`), повторно после перезапуска не показывается; всё полученное остаётся во «Входящих» Ombra.
- Входящие K4-метки в Nightly и синхронизация командных групп B1 (группа как живой общий объект) в этом решении не делаются: группа отправляется снимком как коллекция.

**Остаточные риски (заявляем явно):**
1. Сервер видит metadata: membership (memberId/deviceId), кто, когда и кому отправляет (адресная отправка идёт через парную группу, дескриптор которой в PublicMessage-handshake содержит оба memberId, поэтому граф адресатов виден), число копий, размеры, IP; handshake раскрывает дерево и KeyPackage (D-10). Срок хранения: IP и access-лог — 14 дней, audit — 1 год, очередь доставки — до ack, но не дольше 30 дней, передачи — до ack, но не дольше 24 ч, бэкапы (без очереди и передач) — по ротации оператора, по умолчанию 14 дней (настраивается).
2. Уже полученное удалённым не отзывается гарантированно: локальная очистка (§5.1 п.6) работает только у честного клиента, который снова вышел на связь; изменённый клиент, клиент без сети, экспортированные файлы, скриншоты и копии, сделанные заранее, остаются у него (D-5).
3. Окно между CLI-удалением и ротацией: новое не отправляется (hold), но то, что было отправлено до блокировки в текущем epoch, удалённый мог получить.
4. Оператор вместе с удалённым участником может держать **изолированного** клиента на старом epoch и читать то, что этот клиент отправит, пока клиент считает состояние подтверждённым: до T, если удалённый — обычный участник или один из ≥ k_hb админов; **без ограничения по времени**, если удалённый — owner (его heartbeat засчитывается сам по себе) или единственный админ при `k_hb = 1`. Защита — heartbeat-кворум, T и сверка safety number.
5. Доступность: сервер может остановить работу (отказ, «заморожена»); E2EE её не обеспечивает.
6. TOFU канала приглашения: перехвативший ссылку целиком вступает вместо адресата; смягчение — персональные ссылки, safety number.
7. В Git-сценарии без провайдерского доказательства безопасность сводится к ручной сверке (Git-сценарий вне этого релиза, §4.4).
8. Потеря всех устройств владельца без ключа восстановления = заморозка команды; выход — переустановка сервера и новая команда (D-3). Кража ключа восстановления при недоступном дольше `timeLock` владельце даёт захват владения. Резервной копии элементов нет (D-7): потеря всех устройств участника — потеря его элементов.
9. Разблокированная память, swap/crash dumps; DPAPI CurrentUser доступен любому процессу пользователя.
10. Equivocation обнаруживается при пересечении клиентов/heartbeat, не мгновенно.
11. FFI (Rust/unsafe) и правила `ombra-core` — **обязательный независимый security review** (ARCH §4).

## 10. Что не делаем

Собственная криптография, CRDT/LWW для прав, P2P, доверенный оператор с одним TLS, серверное хранение plaintext, server-side поиск по содержимому, presigned bearer-ссылки, публикация GroupInfo для external join, резервная копия элементов на сервере (D-7), смена владельца кворумом админов (D-3), чат/лента комментариев/треды/история диалогов (уточнение владельца, §3.0).

| D-4 | Новый участник по умолчанию не видит ранее опубликованные элементы и метки; админ может явно «поделиться элементами» | новичок без контекста, пока админ не поделится; переданные элементы подлинны только по подписям авторов (§3.2) | **ПРИНЯТО** владельцем |
| D-5 | Удалённый сразу теряет доступ к элементам команды: сервер блокирует всё немедленно, приложение сразу делает Remove/ротацию, честный клиент удалённого стирает локальные данные команды (best-effort). При CLI-удалении до ротации новые элементы держатся в outbox | изменённый/офлайн клиент и заранее сделанные копии не отзываются; при всех админах offline после CLI-удаления команда не публикует элементы до ротации — оператор может так остановить работу, но не прочитать | **ПРИНЯТО** владельцем |

| D-7 | Резервной копии элементов на сервере нет; сервер хранит только очередь доставки (до 30 дней) и одноразовые передачи (до 24 ч); обе исключены из бэкапов, после restore пусты | при потере всех устройств участника его элементы пропадают; восстановление только переносом с другого своего устройства или «поделиться элементами» | **ПРИНЯТО** владельцем (убрано из проекта) |
| D-8 | Blob-ы на ФС сервера по умолчанию, S3 — только через прокси сервера | рост диска сервера; при S3 — нагрузка проксирования и ещё одна система с ciphertext и metadata | **ПРИНЯТО** (рекомендация) |
