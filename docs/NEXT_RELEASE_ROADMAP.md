### Противоречия, которые нельзя переносить в реализацию

1. Прежний запрет форка снят решением владельца 2026-10-15; README, ROADMAP, PROJECT_STATE и notices обновлены. Исходники общего движка интегрированы; бета пинит `ombra-engine-18.12.2-bun-1.4.2-v1`. Предыдущий clean-install на macOS проверял 18.8.0, не новый pin; опубликованная подписанная поставка и другие ОС остаются отдельными gates.
2. Ранее клиент запускал omp отдельно на каждый чат; это не согласованная архитектура беты. Требуется общий исходный движок приложения с изолированными логическими `AgentSession`, без CLI/VM/Worker на чат и без spare-процессов. Старые статусы PROJECT_STATE/PARITY_ROADMAP требуют сверки с кодом и запуском, а не сохранения прежнего процессного устройства под названием «форк».
3. D4 уточнён повторно: одного external-only bridge недостаточно. Отдельный процесс Nightly должен отдавать интерактивную поверхность в Ombra; проверить кадры, ввод, скрытый рендер, IME/DPI и задержку. Исключать эти риски из K1 было ошибкой.
4. P4 предлагает add-wins для множеств. **Членство, доступ, отзыв устройства и владение не должны восстанавливаться устаревшей офлайн-записью.** Для них нужна серверная авторизация и отдельные правила конфликтов.
5. «После logout ничего не уходит» в K2 уточнить как отсутствие запросов **к сервису платформы**. В продукте уже есть обновления, model providers и загрузки runtime; глобальный запрет сети — другой контракт.
6. Имена файлов и текст шага плана тоже могут раскрывать секреты. Opt-in прогресса должен перечислять реальные поля, а redactor не может обещать обнаружение всех секретов.
7. Поиск по зашифрованному индексу B3 и старт 5 000 изображений за ≤1 с требуют совместной проверки. Нельзя сначала построить открытый FTS/SQLite, а затем объявить шифрование завершённым после шифрования PNG.

### Размещение браузера и редактора — уточнение владельца

Браузер K1 и редактор K7 встраиваются в контейнер рабочей области **внутри окна Ombra** — тёмную внутреннюю область на предоставленном владельцем скриншоте. Это содержимое интерфейса Ombra, а не отдельное обязательное окно приложения, внешнее окно поверх панели или видеозеркало без полноценного ввода. Конкретную компоновку вкладок и соседних панелей проверить на UX/UI review; скриншот фиксирует место встраивания, не новый окончательный макет. **Уточнение 2026-10-18:** внутри агента браузер открыт в правой панели, его используют инструменты агента, аннотации сохраняются. Для самостоятельной работы браузер открывается из левого rail — та же вкладка общего runtime. Вынос в отдельное окно не делаем.

- Общая оболочка Ombra управляет геометрией контейнера, переключением содержимого и фокусом. Браузерная поверхность и редактор соблюдают его границы, clipping и resize; не перекрывают соседние панели.
- Nightly runtime может работать отдельным фоновым процессом, но его интерактивная поверхность отображается внутри этого контейнера. Отдельное окно Nightly для работы не требуется. Редактор — встроенный native control, не запускаемый внешний IDE.
- Приёмка K1/K7: открыть страницу и файл внутри Ombra, проверить переключение без потери состояния и несохранённых правок, resize/DPI, клавиатуру/IME, передачу фокуса между чатом и содержимым, меню и отсутствие перехвата ввода скрытой панелью. Проверка на реальном UI входит в пофичевые QA и UX/UI review.

## 4. Порядок реализации

### Обязательный цикл каждой фичи: QA → UX/UI review → security check

Действует для всех функциональных потоков Ombra/Nightly/backend/runtime и существенных изменений после review. Ранее перечисленные общие gates не заменяют эту пофичевую приёмку. Фича не помечается завершённой до закрытия всех трёх проверок; объём проверок определяется затронутыми сценариями и границами доверия, а не размером diff.

До реализации фиксируются пользовательский сценарий, критерии приёмки, затронутые ОС/компоненты и риски. UX и security решения, влияющие на архитектуру, проверяются до написания зависимого кода; итоговый review выполняется на работающей фиче.

1. **QA:** пройти основной и негативные сценарии на реальной сборке; проверить границы, отмену/повтор, ошибки, сохранность и восстановление, offline/reconnect и миграции там, где применимо. Выполнить релевантные автоматические регрессионные/контрактные проверки и smoke затронутых интеграций. Заглушки и compile-only не заменяют настоящий UI/runtime; результат каждой ОС записывается отдельно, непроверенная платформа не получает PASS.
2. **UX/UI review:** пройти полный пользовательский путь в приложении, а не оценивать только макет. Проверить понятность действий и разрешений, число шагов, обратную связь, empty/loading/error/offline/conflict состояния, отмену и восстановление; согласованность Ombra/Nightly, keyboard/focus/IME, accessibility, DPI/resize, длинный текст и локализацию. Зафиксировать screenshots/короткую запись и найденные проблемы без приватных данных. Для изменений без UI — обосновать N/A визуальной части и проверить потребительский сценарий, если он затронут.
3. **Security check:** проверить изменённые trust boundaries и потоки данных: auth/ACL/revoke, изоляцию проектов/пользователей, permissions инструментов, недоверенные MCP/skills/вложения/страницы, секреты и логи, пути/URL/команды, зависимости/поставку и хранение. Для затронутых границ выполнить негативные runtime-сценарии; статический анализ и dependency/secret scanning дополняют ручной review, но не доказывают безопасность сами по себе. Отсутствие новой границы фиксируется с обоснованием, не означает автоматический пропуск.

Проверки могут идти параллельно после готовности сборки. По каждой фиче сохраняется запись: ID требования, commit/build, окружение/ОС, проверяющий, сценарии и доказательства, PASS/FAIL/BLOCKED/обоснованное N/A, список дефектов и результат повторной проверки. Для чувствительных к безопасности изменений обязателен reviewer, не являющийся автором изменения; отсутствие reviewer означает BLOCKED, а не самоподтверждение.

**Закрытие:** блокирующие функциональные/UX/security дефекты исправлены; неблокирующие остатки явно приняты ответственным с риском и решением, а не забыты. После исправления повторяются затронутые проверки и соседние сценарии; evidence относится к итоговой версии. Изменение поведения после PASS требует повторной приёмки затронутой части.

Пофичевые reviews не отменяют сквозную интеграционную приёмку. После обязательного этапа 8 на итоговой RC-сборке повторяются QA, UX/UI и security review всего продукта, включая межкомпонентные сценарии и накопленные изменения.

### Этап 4. K1: общий Nightly runtime и замена движка preview

**Зависит от proof интерактивной поверхности, ввода и локального bridge D4. External-only не закрывает этап.**

1. Один versioned Nightly runtime build и browser API для standalone, всех browser/preview панелей Ombra и web-режима K3. Автоматический аутентифицированный bootstrap и workspace/session/tab ownership; без ручной передачи вкладок и без доступа к личным вкладкам. Независимость приложений не требует независимых browser engines.
   - Полный сценарий «только Ombra»: создание/закрытие/переключение нескольких вкладок, адресная строка, назад/вперёд/reload, сохранение и восстановление вкладок после перезапуска. Runtime запускается автоматически в фоне, отдельное окно Nightly не требуется.
   - Runtime поставляется вместе с Ombra либо устанавливается через Ombra при первом использовании браузера. Самостоятельный Nightly — независимый дополнительный интерфейс; вынос/возврат той же вкладки необязателен и не создаёт копию.
2. Локальный аутентифицированный канал: права сокета/pipe, секрет вне страницы, привязка к сессии и вкладке, закрытие доступа при disconnect. На Windows нужны ACL, а не буквальный перенос Unix `0600`.
3. Навигация, чтение, input, eval, screenshots, lifecycle вкладок; явные ошибки неподдерживаемых возможностей. Контрактная матрица для dialogs/files/downloads/frames, а не молчаливая потеря существующего preview-поведения.
4. Аннотации и маршруты SPA; привязка к проекту и чату; заметная индикация управления; пользовательский ввод приостанавливает агента; Stop отменяет дальнейшие действия.
5. Consent `once/session/always` на origin и действие. Проверка после redirect/navigation; страница и её prompt injection не могут выдать себе разрешение. Не полагаться на ненадёжное определение «пользователь залогинен».
6. Поверхность настоящей вкладки внутри Avalonia, пользовательский ввод и browser chrome; вынос/возврат той же вкладки без перезагрузки. Проверить скрытый рендер, IME/focus, DPI/resize, clipboard, drag/drop, popup/dialogs, audio/video, accessibility и стоимость транспорта на трёх ОС.
7. Перевести `PreviewPanel`/`PreviewTab`, Tern/cmux consumers, popups, native hooks/input/capture, engine settings и web-device preview на общий backend с сохранением поведения; удалить старые engine adapters/WebView dependency и скрытый Chromium fallback после cutover. Перенести данные без обещания автоматического импорта web credentials.
8. Runtime delivery: совместимая установленная сборка или проверенный pack; подпись, integrity, protocol/capabilities, profile compatibility, update/recovery. Не обновлять бинарники под живым процессом. Нет runtime — явная установка/ошибка, а не молчаливый старый WebView.

**Выход:** нынешний preview и browser tools работают на общем Nightly runtime прямо в Ombra без ручного pairing; вынос/возврат сохраняет состояние. Сохранены annotations/dialogs/auth/downloads/permissions и пользовательский Stop. Полный функциональный cutover без второго browser engine, миграция данных и сравнение standalone/embedded на трёх ОС доказаны. Только bridge или отдельная новая панель не закрывают этап.

**Обязательный сценарий приёмки «только Ombra»:** на чистой установке без самостоятельного Nightly получить runtime штатным способом, открыть несколько вкладок в Ombra, пройти вход на тестовый сайт, использовать навигацию/загрузку/popup, выполнить действие агента в той же вкладке, перезапустить Ombra и восстановить вкладки. Ни ручного запуска второго приложения, ни pairing/передачи вкладки для этого не требуется. Отдельно проверить независимый запуск Nightly и необязательный вынос/возврат вкладки без потери её текущего состояния.

### Этап 5. P1–P4: общая платформа

**Зависит от D1; контракт данных согласуется до параллельного UI.**

1. **P1:** собственный участник — `memberId` и имя, устройства и revoke; учётная запись Git-провайдера не используется (решение владельца 2026-10-18). Локальная работа без аккаунта сохраняется.
2. **P2:** только собственные команды — создатель становится владельцем, владелец добавляет участников (по ID или приглашению) и удаляет их, назначает доступ к проектам, передаёт владение. Привязка проекта по remote URL без credentials. Команды из доступа к репозиторию у Git-провайдера — **не в этом релизе** ([ARCHITECTURE_SOLUTIONS §10.1](ARCHITECTURE_SOLUTIONS.md#101-участники-и-права) заменён решением владельца).
3. **P4 foundation:** локальная SQLite-реплика, outbox, idempotency, серверный курсор и догон, версии схем, tombstones, правила конфликтов. Авторизация проверяется на сервере для каждого действия и подписки; время клиента не определяет права.
4. **P3:** opt-in издатель прогресса с debounce; фильтрация доступа, presence, подписки по проекту. Не отправлять prompts/content/diff и локальные абсолютные пути.
5. **P4 consumers:** общие Groups, Requests, replies и разрешённые attachments. Отзыв доступа блокирует новые события/записи и очищает доступные приложению кэши; уже полученное человеком содержимое отозвать невозможно.

**Выход:** два клиента на разных машинах, offline/reconnect без дублей; прогресс ≤2 с; добавление и удаление участника, передача владения и отзыв доступа в собственных командах; отключённый аккаунт не обращается к платформе. До публичного сервера проверены backup/restore, обновление схем и восстановление ключей согласно D1.

### Этап 6. K2/K4/B2 и командная часть B1

- **K2:** Account, устройства, Git-команды, роли/ограничения видимости, проекты/фильтры/presence и opt-in активность по веткам; без обязательного workflow задач. Управление владельцем — только для самостоятельных non-Git команд.
- **K4 local:** унифицировать page/code/diff comments в Request; отправка агенту может идти раньше сервера. Не терять старые локальные комментарии при миграции.
- **K4 shared:** входящие в обоих продуктах; thread/status; «Принять → агенту» только после действия пользователя; anchors по commit/excerpt, неоднозначный или исчезнувший anchor показывать честно.
- **B2:** отправка URL/comment/selection/screenshot/annotation участнику и команде; preview данных до отправки; общая политика redaction для C# и JS с одинаковыми примерами, а не обещание прямого reuse C# regex в Firefox.
- **B1 team:** синхронизируемые подборки ссылок, публикация локальной группы, открытие подборки как вкладок; временные вкладки автоматически в облако не уходят.
- **Обмен ресурсами:** адресные сообщения и mentions, файлы/картинки, code snippets/patches, MCP recipes без секретов, versioned skills и библиотека рекомендуемых ресурсов. Получение не запускает код; установка/активация/разрешения разделены.
- **Запрос merge:** read-only участник отправляет PR/MR либо patch с base commit; уполномоченный коллега рассматривает и сливает под своими правами с checks/branch protection. Provider — источник истины, не второй PR-трекер. Приёмка и последующее развитие project setup/«сохранить как skill» — ARCHITECTURE_SOLUTIONS §10.

**Выход:** Nightly → другой участник в Ombra → исходный anchor → подтверждённая отправка агенту → ответ/статус синхронизированы. Сдвинутые строки находятся правильно; чужой проект не раскрывается через входящие/вложения. Удаление оригинала системного скриншота — только с явным подтверждением.

### Этап 8. Обязательный интеграционный рефакторинг перед RC

**Требование владельца:** отдельный обязательный этап после завершения и интеграции всех функциональных потоков этого релиза, включая командную работу, обмен ресурсами и запрос merge. Не переносить за выпуск беты и не подменять форматированием. Локальные исправления архитектуры и удаление устаревших путей при cutover выполняются сразу; финальный этап не оправдывает накопление заведомо опасных обходов.

**Вход:** функциональные критерии предыдущих этапов подтверждены, версии компонентов закреплены, имеются воспроизводимые сценарии и профили до рефакторинга. Новые функции на этом этапе не добавляются.

**Работы:**
- Провести сквозной аудит границ модулей и ownership: sessions/processes, document/LSP, browser host/surfaces, devices, sync/ACL и shared resources. Устранить дублирующих владельцев состояния, расходящиеся правила и циклические зависимости.
- Удалить оставшиеся временные адаптеры, старые backend/call paths, неиспользуемые flags/config и обходы, ставшие ненужными после fork/cutover. Мигрировать всех потребителей, не оставлять бессрочные compatibility shims. Сохранить необходимые проверенные миграции пользовательских данных.
- Консолидировать действительно одинаковые contracts, permission checks, сериализацию, обработку ошибок, cancellation/disposal и ограничение очередей. Не создавать универсальные абстракции без реальных потребителей и не объединять платформенные реализации только ради одинакового вида.
- Упростить чрезмерно связанные controllers/view models/services небольшими проверяемыми изменениями. Сохранить поведение и публичные контракты; необходимое изменение протокола или схемы требует явной версии и миграционного доказательства.
- По повторным профилям убрать лишние копирования, аллокации, повторные вычисления и неограниченное удержание памяти. Обновить архитектурную документацию и правила дальнейшего обновления форков.

**Выход / release gate:** реестр найденных проблем содержит решение и доказательство для каждого пункта; блокирующие проблемы закрыты, остаточные неблокирующие явно обоснованы. На итоговой сборке повторены contract/regression проверки, реальные UI/runtime сценарии и профили относительно baseline: сохранность/восстановление, Stop/process cleanup, editor conflicts, общий Nightly, устройства, командный обмен/merge, revoke, update/migrations. Нет необъяснённых регрессий корректности, безопасности или производительности. Проверки выполнены на целевых ОС; compile-only не заменяет запуск.

У этапа отдельный интеграционный владелец и зарезервированное место в календаре после функциональной интеграции и до RC. Длительность определяется аудитом, не фиктивной фиксированной оценкой. Только после его приёмки начинается финальная RC-проверка и выпуск.

Нужны владельцы потоков: Ombra/RPC; Nightly/browser bridge; backend/sync/security; устройства; интеграция/release. Это роли, не предположение о наличии пяти исполнителей. На shared contracts и миграции — один интеграционный владелец; API согласовать до разделения UI по репозиториям.
